# SSU2 transport and reachability

Status: **required**  
Primary roadmap milestone: **8**  
Role: current UDP router transport, reachability testing and relay

## Scope

SSU2 provides authenticated point-to-point transport of I2NP messages over UDP. It includes handshake and data phases, packet-number and acknowledgement processing, loss recovery, I2NP fragmentation/reassembly, address validation/tokens, relay for NAT traversal, peer testing and connection migration.

SSU2 is semi-reliable and message-oriented. It does not provide an ordered byte stream or guaranteed delivery. I2NP messages may arrive out of order, may be delivered more than once, or may fail while the session remains usable.

## Authoritative sources

- [SSU2 specification](https://i2p.net/en/docs/specs/ssu2/), pinned in [SOURCES.md](../SOURCES.md), completed and accurate for 0.9.69 at the snapshot.
- [Proposal 159](https://github.com/i2p/i2p.website/blob/88596022920bdf99f27db27688faf4f204792fcd/static/proposals/159-ssu2.txt) for design/threat background.
- [Proposal 165](https://github.com/i2p/i2p.website/blob/88596022920bdf99f27db27688faf4f204792fcd/static/proposals/165-ssu2-fix.txt) for deployed corrections.
- NTCP2, ECIES and common-structures specifications for shared crypto/block concepts.
- Noise, RFC 7748 and the QUIC/WireGuard references named by the SSU2 document.

SSU2 adapts concepts from QUIC and WireGuard but is neither protocol. Implement only behavior explicitly specified by SSU2.

## Plan 156 establishment scope (2026-09-04)

Plan 156 implements the complete runtime-neutral establishment
protocol inside `i2pr-transport-ssu2` (still no UDP sockets, no
runtime service):

- Noise XK transcript (`crypto.rs`) for the SSU2-specific pattern
  `Noise_XKchaobfse+hs1+hs2+hs3_25519_ChaChaPoly_SHA256`, with
  role-gated consuming transitions, retained `es` cipher for the
  static-key frame, and `split()` directional keys.
- ChaCha20 header protection exactly per the Header Encryption KDF
  pseudocode (which governs over the raw-contents `n: 1`
  annotation; see the module docs), Retry/TokenRequest AEAD under
  the intro key, and the `SessCreateHeader` / `SessionConfirmed` /
  `HKDFSSU2DataKeys` labeled derivations.
- Strict TokenRequest/Retry/SessionRequest/SessionCreated codecs,
  symmetric-only cheap prevalidation before DH/session allocation,
  bounded SessionConfirmed fragmentation/reassembly (≤15
  fragments, 32 KiB aggregate, RouterInfo-first enforcement).
- Bounded one-use token lifecycle (`token.rs`): 8-byte values bound
  to the exact source endpoint, 30 s default lifetime, 256-global /
  4-per-source quotas with deterministic oldest-eviction, rotate
  (restart) invalidation, and the 3x Retry amplification budget.
- Deep RouterInfo establishment binding: structural decode,
  signature, expected-hash check, `v=2` address presence,
  static-`s` binding, intro-`i` shape, and caller-supplied
  publication freshness — without mutating NetDB.
- Consuming initiator/responder machines emitting bounded
  `WriteDatagram` / `ArmDeadline` / `Established` / `Terminate` /
  `DropSilently` actions on the specification resend schedules
  with a 20 s terminal deadline.

Evidence: `crates/i2pr-transport-ssu2/tests/handshake.rs` (20
trajectories), 6 committed handshake vectors in
`tests/fixtures/ssu2/` (one with raw-primitive independent
derivation), and `plans/156-status.md`. Interoperability and UDP
runtime binding remain Plans 158–161 scope; the data phase is Plan
157 scope below.

## Plan 157 data-phase scope (2026-09-04)

Plan 157 implements the complete runtime-neutral data phase inside
`i2pr-transport-ssu2` (still no UDP sockets, no runtime service):

- Authenticated `Ssu2Session` (`session.rs`) consuming the
  establishment keys: short-header protection (`k_header_1` as the
  receiver intro key, `k_header_2` from the corrected two-step
  `HKDFSSU2DataKeys` derivation), ordered receive pipeline (length →
  binding → unprotection → replay check → AEAD → block parse →
  effects), and single-seal transmit with header protection.
- Full packet-number window (128-packet bounded bitmap, duplicate /
  too-old / future-jump rejection, wrap and exhaustion handling; the
  v2 short header carries the full number, so reconstruction is the
  documented identity plus window policy).
- Strict ACK range interpretation (underflow/degenerate rejection,
  retire-only-sent, idempotent duplicates) with loop-free scheduling
  (one per-session deadline; delayed/immediate horizons from the
  specification guidance; ACK-only congestion exception).
- Fresh-packet retransmission (never cached ciphertext) with
  per-fragment ceilings and silent per-message failure while the
  session stays usable; RFC 6298-style RTT/RTO with a conservative
  byte-count congestion controller (documented local policy where the
  specification defers).
- Exact MTU-aware I2NP fragmentation (fixed semantic fragments,
  complete-block fast path, 64-fragment ceiling) with strict
  reassembly quotas (16 messages / 256 KiB), conflict-drop, expiry,
  atomic once-only completion, and a bounded delivered-ID duplicate
  cache.
- Data-phase control as typed events (NewToken handoff, DateTime /
  Options / Congestion observation, path challenge/response plumbing
  without migration, opaque relay/peer-test events, `NextNonce` rekey
  boundary without automatic rekey, `FirstPacketNumber` without
  renumbering), termination with bounded cleanup, idle timeout, and
  privacy-safe counters.

Evidence: `crates/i2pr-transport-ssu2/tests/data_phase.rs` (17
trajectories), unit boundary tests in `session.rs`, 2 committed
data-phase vectors in `tests/fixtures/ssu2/` reproduced byte-for-byte
through the session path, and `plans/157-status.md`. UDP runtime
binding and interoperability remain Plans 158–161 scope.

## Plan 159 path/publication/selection scope (2026-09-04)

Plan 159 keeps every Plan 158 socket/admission/promotion invariant
and adds, without changing wire semantics:

- Authenticated path validation (`i2pr-transport-ssu2::path`):
  a new-endpoint packet authenticates against the existing session
  first and opens at most one bounded candidate (4 per session, 2
  per family, 8 challenges per session, 32-byte challenge,
  10 s deadline); only the matching authenticated PathResponse
  promotes; expiry retains the old path; candidate MTU is pinned to
  the 1280 minimum; no packet claim can raise the validated MTU.
- Migration congestion reset (`Ssu2Session::note_path_migrated`):
  unacked sent packets requeue through the bounded loss policy so
  they retransmit fresh on the new path; flight resets to zero and
  the window to its minimum.
- Conservative reachability (`i2pr-transport::reachability`):
  family-only signals accumulate into
  Unknown/ObservedUnconfirmed/CandidateReachable/Reachable/
  Firewalled/Unreachable with a validation-enforced corroboration
  floor of two — one peer observation can never publish
  `Reachable` — plus contradiction downgrade and evidence expiry.
- Publication snapshots (`i2pr-transport-ssu2::publication`):
  deterministic canonical option entries from public keys only;
  direct host/port requires `Reachable` plus explicit opt-in;
  otherwise the unpublished static-only firewalled form; snapshots
  carry evidence expiry for withdrawal. No production publication
  is enabled.
- Deterministic selection (`i2pr-transport::selection`):
  reuse-before-dial, per-transport structural validity, backoff,
  direct-before-introducer-only, enablement, deterministic
  tie-break, and peer limits, with `DialFallback` across transports
  and address-failure isolation.

Runtime wiring (`i2pr-runtime`): per-session validators driven after
session authentication, single-shot minimum-MTU challenges/answers,
migration with IP/subnet accounting moves, scheduler-owned expiry,
and privacy-safe snapshot counters. Daemon `[ssu2]` activation and
non-loopback dials stay fail-closed.

Evidence: `crates/i2pr-transport-ssu2/tests/path_validation.rs` (9
real sealed-packet trajectories), inline unit matrices for all four
new modules, 3 real-UDP tests inline in `ssu2_runtime.rs`
(migration both directions with behavioral delivery proof, spoof
boundedness, control round trip), and `plans/159-status.md`. Peer
test/relay roles belong to Plan 160; independent interop to
Plan 161.

## Plan 160 peer-test/relay scope (2026-09-04)

Plan 160 implements the SSU2 v2 reachability mechanisms for ordinary
firewalled-router operation without changing wire semantics and
without enabling production publication:

- PeerTest roles (`i2pr-transport-ssu2::peer_test`): Alice/Bob/Charlie
  with nonce correlation (8 global, 2 per peer, 10 s central-expiry
  deadlines), exact `PeerTestValidate` signature preimages (Msgs 1,2
  Alice-signed without `ahash`; Msgs 3,4 Charlie-signed with `ahash`;
  Msgs 5–7 optional), ±120 s freshness, role/state/sender/family
  gates, idempotent duplicates, and typed outcomes
  (`DirectReachabilityConfirmed` / `AddressMismatch` /
  `FirewalledLikely` / `Inconclusive` / `Rejected`). Msg 4 alone never
  confirms; unsigned Msgs 5–7 never confirm alone; contradictory
  observations yield `AddressMismatch`, never last-write-wins.
- Relay roles (`i2pr-transport-ssu2::relay`): requester (bounded
  concurrent requests, response/tag/nonce correlation, HolePunch
  verification, transition to the normal handshake path),
  introducer (disabled by default; live-tag checks, per-peer/global
  quotas, 3x anti-amplification budget, replay idempotency,
  deterministic expiry, shutdown clears state), target (introducer-
  context validation, single HolePunch emission per intro with replay
  suppression). Exact `RelayRequestData` / `RelayAgreementOK`
  preimages; nonce-derived HolePunch connection IDs
  (`Dest = (nonce << 32) | nonce`, `Src = !Dest`); intro-key AEAD
  HolePunch and out-of-session PeerTest codecs.
- Introducer records (`i2pr-transport-ssu2::introducer`): one bounded
  owner (8 records, 3 published, deterministic oldest-expiry
  replacement, expiry withdrawal, failed-peer removal) feeding the
  Plan 159 publication builder's validated `Ssu2Introducer` inputs.
- Reachability consumption (`i2pr-transport::reachability`): typed
  `PeerTestOutcomeKind` (`Confirmed` supports; `AddressMismatch` /
  `FirewalledLikely` contradict; `Inconclusive` / `Rejected` neutral
  so inconclusive tests never flip state); relay success feeds
  `RelayFirewalledSignal` and never proves direct reachability.
- Session carriage (`session.rs`): full relay/peer-test blocks as
  typed `SessionEvent`s (no longer opaque) plus single-shot bounded
  `queue_relay_request/response/intro` and `queue_peer_test` controls.
- Runtime coordination (`i2pr-runtime::Ssu2PeerRelayService`): table
  ownership, per-source rate limits (8/sec, 1024 sources, cheap-drop
  before crypto), bounded signer registry, central expiry scheduler,
  `RelayFirewalledSignal` mirroring, validated-introducer selection,
  shutdown-to-baseline, and privacy-safe snapshots/counters.
  Introducer service stays disabled by default.

Only Ed25519 router signatures verify in this pass
(multi-algorithm interop is Plan 161 debt); RouterInfo signing-key
plumbing into the runtime is deferred (tests register keys
explicitly). Daemon `[ssu2]` activation and non-loopback dials stay
fail-closed.

Evidence: `crates/i2pr-transport-ssu2/tests/peer_relay.rs` (8
sealed-packet trajectories), inline unit matrices for all new
modules, `crates/i2pr-runtime/tests/ssu2_peer_relay.rs` (7 real-UDP
NAT-like tests: direct with NAT rewrite, mismatch/inconclusive,
flood boundedness, relay-to-handshake product path, expiry/disabled/
shutdown, concurrency isolation, publication/privacy), and
`plans/160-status.md`. Independent interop belongs to Plan 161.

## Required MVP behavior

### Address publication and socket model

- Parse/publish current SSU2 RouterAddress options, static key, introducer/relay information and reachability fields.
- Use separate IPv4 and IPv6 socket/listener state where needed for correct address and migration handling.
- Keep observed external addresses and publication decisions outside the packet codec.
- Do not publish a directly reachable address until peer-test/observation policy supports it.

### Admission, tokens and handshake

Implement explicit initiator/responder states for:

- session request/created/confirmed messages;
- retry/address-validation token issuance and validation;
- fragmented RouterInfo in establishment where required;
- transcript/KDF/header protection and authenticated payloads;
- timestamp, network-ID, peer identity and source-address checks;
- replay/duplicate establishment handling.

Token validation must occur before avoidable expensive cryptographic work. Token keys require rotation, bounded overlap and restart semantics. Invalid/spoofed-source traffic must not create unbounded per-source state.

### Data phase

Implement:

- packet header parsing, obfuscation/protection and connection IDs;
- packet-number reconstruction and replay window;
- authenticated block parsing;
- ACK ranges/NACK or loss inference as specified;
- retransmission of I2NP fragments without promising ordered I2NP delivery;
- I2NP message fragmentation/reassembly with strict budgets;
- immediate-ACK and termination behavior;
- session key rotation/rekeying;
- idle timeout and clean teardown;
- duplicate I2NP suppression at the I2NP layer in addition to packet replay checks.

Loss recovery and congestion behavior must be bounded and stable under severe loss. Avoid one task or timer per packet.

### Relay and peer test

Implement current relay roles and messages required for ordinary firewalled-router operation:

- introducer advertisement/selection;
- relay request/response/introduction;
- signed data verification and freshness;
- per-peer/IP quotas and anti-amplification checks;
- peer testing for inbound reachability and address agreement;
- state transitions that cannot be confused across concurrent tests.

A relay or peer-test response must not cause address publication from a single unauthenticated observation.

### Migration/path validation

Support source-address changes only through specification-defined validation. Do not migrate an established peer merely because an authenticated-looking packet arrives from a new address without the required path challenge/response or equivalent state.

## Security and resource requirements

- Bound datagram size before parsing and drop impossible packets cheaply.
- Separate stateless/low-state prevalidation from allocated session state.
- Rate-limit token generation, Retry, relay and peer-test responses by source and globally.
- Prevent amplification by enforcing response-size and validation rules.
- Bound active sessions, pending handshakes, packet histories, ACK ranges, retransmissions and reassembly bytes.
- Reject packet-number replays and excessively old/future windows.
- Use constant-time authentication through reviewed crypto libraries.
- Avoid reflecting detailed parse/authentication failures.
- Release packet buffers and resource permits on cancellation, migration failure and timeout.

## Required tests

- Fixed handshake/KDF/header-protection vectors for initiator and responder.
- Interoperability in both directions with Java I2P and i2pd over IPv4; IPv6 where infrastructure permits.
- Spoofed-source request floods proving bounded crypto and state.
- Token valid/invalid/expired/wrong-address/key-rotation/restart cases.
- Packet-number reconstruction, duplicate, replay-window and wrap boundaries.
- ACK ranges, loss/retransmission, severe reordering and duplicate datagrams.
- I2NP fragment loss/reorder/duplicate/conflict and reassembly pressure.
- Key rotation and termination.
- Relay requester, introducer and target roles with invalid signatures/freshness.
- Concurrent peer tests, contradictory observations and reachability transitions.
- Migration/path validation with spoofed and legitimate address changes.
- NAT-like deterministic simulation, queue saturation and cancellation.
- Fuzzing of authenticated plaintext blocks, ACKs and fragment structures.

## Deferred and excluded behavior

- SSU1: legacy-reject; the MVP excludes SSU1.
- Shared SSU1/SSU2 compatibility paths: deferred unless unavoidable for current address parsing.
- IPv6 publication without end-to-end test infrastructure: may be `required-later`, but parser/socket architecture must not preclude it.
- Exotic migration/multihoming behavior: deferred beyond specification-required ordinary address changes.
- Experimental flow-control extensions: deferred.
- Public introducer service: disabled until controlled resource/abuse testing passes even if relay-client support is complete.
