# SSU2 transport and reachability

Status: **required**  
Primary roadmap milestone: **8**  
Role: current UDP router transport, reachability testing and relay

## Scope

SSU2 provides authenticated point-to-point transport of I2NP messages over UDP. It includes handshake and data phases, packet-number and acknowledgement processing, loss recovery, I2NP fragmentation/reassembly, address validation/tokens, relay for NAT traversal, peer testing and connection migration.

SSU2 is semi-reliable and message-oriented. It does not provide an ordered byte stream or guaranteed delivery. I2NP messages may arrive out of order, may be delivered more than once, or may fail while the session remains usable.

## Authoritative sources

- [SSU2 specification](https://i2p.net/en/docs/specs/ssu2/), pinned in [SOURCES.md](../SOURCES.md), completed and accurate for 0.9.69 at the snapshot.
- [Proposal 159](https://github.com/i2p/i2p.website/blob/88596022920bdf99f27db27688faf4f204792fcd/static/proposals/159-ssu2.txt) for design/threat background.
- [Proposal 165](https://github.com/i2p/i2p.website/blob/88596022920bdf99f27db27688faf4f204792fcd/static/proposals/165-ssu2-fix.txt) for deployed corrections.
- NTCP2, ECIES and common-structures specifications for shared crypto/block concepts.
- Noise, RFC 7748 and the QUIC/WireGuard references named by the SSU2 document.

SSU2 adapts concepts from QUIC and WireGuard but is neither protocol. Implement only behavior explicitly specified by SSU2.

## Plan 156 establishment scope (2026-09-04)

Plan 156 implements the complete runtime-neutral establishment
protocol inside `i2pr-transport-ssu2` (still no UDP sockets, no
runtime service):

- Noise XK transcript (`crypto.rs`) for the SSU2-specific pattern
  `Noise_XKchaobfse+hs1+hs2+hs3_25519_ChaChaPoly_SHA256`, with
  role-gated consuming transitions, retained `es` cipher for the
  static-key frame, and `split()` directional keys.
- ChaCha20 header protection exactly per the Header Encryption KDF
  pseudocode (which governs over the raw-contents `n: 1`
  annotation; see the module docs), Retry/TokenRequest AEAD under
  the intro key, and the `SessCreateHeader` / `SessionConfirmed` /
  `HKDFSSU2DataKeys` labeled derivations.
- Strict TokenRequest/Retry/SessionRequest/SessionCreated codecs,
  symmetric-only cheap prevalidation before DH/session allocation,
  bounded SessionConfirmed fragmentation/reassembly (≤15
  fragments, 32 KiB aggregate, RouterInfo-first enforcement).
- Bounded one-use token lifecycle (`token.rs`): 8-byte values bound
  to the exact source endpoint, 30 s default lifetime, 256-global /
  4-per-source quotas with deterministic oldest-eviction, rotate
  (restart) invalidation, and the 3x Retry amplification budget.
- Deep RouterInfo establishment binding: structural decode,
  signature, expected-hash check, `v=2` address presence,
  static-`s` binding, intro-`i` shape, and caller-supplied
  publication freshness — without mutating NetDB.
- Consuming initiator/responder machines emitting bounded
  `WriteDatagram` / `ArmDeadline` / `Established` / `Terminate` /
  `DropSilently` actions on the specification resend schedules
  with a 20 s terminal deadline.

## Plan 157 data-phase scope (2026-09-04)

Plan 157 implements the complete runtime-neutral data phase inside
`i2pr-transport-ssu2` (still no UDP sockets, no runtime service):

- Authenticated `Ssu2Session` (`session.rs`) consuming the
  establishment keys: short-header protection (`k_header_1` as the
  receiver intro key, `k_header_2` from the corrected two-step
  `HKDFSSU2DataKeys` derivation), ordered receive pipeline (length →
  binding → unprotection → replay check → AEAD → block parse →
  effects), and single-seal transmit with header protection.
- Full packet-number window (128-packet bounded bitmap, duplicate /
  too-old / future-jump rejection, wrap and exhaustion handling; the
  v2 short header carries the full number, so reconstruction is the

- Strict ACK range interpretation (underflow/degenerate rejection,
  retire-only-sent, idempotent duplicates) with loop-free scheduling
  (one per-session deadline; delayed/immediate horizons from the
  specification guidance; ACK-only congestion exception).
- Fresh-packet retransmission (never cached ciphertext) with
  per-fragment ceilings and silent per-message failure while the
  session stays usable; RFC 6298-style RTT/RTO with a conservative
  byte-count congestion controller (documented local policy where the
  specification defers).
- Exact MTU-aware I2NP fragmentation (fixed semantic fragments,
  complete-block fast path, 64-fragment ceiling) with strict
  reassembly quotas (16 messages / 256 KiB), conflict-drop, expiry,
  atomic once-only completion, and a bounded delivered-ID duplicate
  cache.
- Data-phase control as typed events (NewToken handoff, DateTime /
  Options / Congestion observation, path challenge/response plumbing
  without migration, opaque relay/peer-test events, `NextNonce` rekey
  boundary without automatic rekey, `FirstPacketNumber` without
  renumbering), termination with bounded cleanup, idle timeout, and
  privacy-safe counters.

## Plan 159 path/publication/selection scope (2026-09-04)

Plan 159 keeps every Plan 158 socket/admission/promotion invariant
and adds, without changing wire semantics:

- Authenticated path validation (`i2pr-transport-ssu2::path`):
  a new-endpoint packet authenticates against the existing session
  first and opens at most one bounded candidate (4 per session, 2
  per family, 8 challenges per session, 32-byte challenge,
  10 s deadline); only the matching authenticated PathResponse
  promotes; expiry retains the old path; candidate MTU is pinned to
  the 1280 minimum; no packet claim can raise the validated MTU.
- Migration congestion reset (`Ssu2Session::note_path_migrated`):
  unacked sent packets requeue through the bounded loss policy so
  they retransmit fresh on the new path; flight resets to zero and
  the window to its minimum.
- Conservative reachability (`i2pr-transport::reachability`):
  family-only signals accumulate into
  Unknown/ObservedUnconfirmed/CandidateReachable/Reachable/
  Firewalled/Unreachable with a validation-enforced corroboration
  floor of two — one peer observation can never publish
  `Reachable` — plus contradiction downgrade and evidence expiry.
- Publication snapshots (`i2pr-transport-ssu2::publication`):
  deterministic canonical option entries from public keys only;
  direct host/port requires `Reachable` plus explicit opt-in;
  otherwise the unpublished static-only firewalled form; snapshots
  carry evidence expiry for withdrawal. The direct form is rendered
  in production under the explicit `ssu2.advertise` opt-in, which is
  **off** by default; the daemon's owner asks the runtime for the
  material and never builds a snapshot of its own, so the transport's
  builder stays the single authority on the question.
- Deterministic selection (`i2pr-transport::selection`):
  reuse-before-dial, per-transport structural validity, backoff,
  direct-before-introducer-only, enablement, deterministic
  tie-break, and peer limits, with `DialFallback` across transports
  and address-failure isolation.

Runtime wiring (`i2pr-runtime`): per-session validators driven after
session authentication, single-shot minimum-MTU challenges/answers,
migration with IP/subnet accounting moves, scheduler-owned expiry,
and privacy-safe snapshot counters. Daemon `[ssu2]` activation and
non-loopback dials stay fail-closed.

Evidence: `crates/i2pr-transport-ssu2/tests/path_validation.rs` (9
real sealed-packet trajectories), inline unit matrices for all four

## Plan 160 peer-test/relay scope (2026-09-04)

Plan 160 implements the SSU2 v2 reachability mechanisms for ordinary
firewalled-router operation without changing wire semantics and
without enabling production publication:

- PeerTest roles (`i2pr-transport-ssu2::peer_test`): Alice/Bob/Charlie
  with nonce correlation (8 global, 2 per peer, 10 s central-expiry
  deadlines), exact `PeerTestValidate` signature preimages (Msgs 1,2
  Alice-signed without `ahash`; Msgs 3,4 Charlie-signed with `ahash`;
  Msgs 5–7 optional), ±120 s freshness, role/state/sender/family
  gates, idempotent duplicates, and typed outcomes
  (`DirectReachabilityConfirmed` / `AddressMismatch` /
  `FirewalledLikely` / `Inconclusive` / `Rejected`). Msg 4 alone never
  confirms; unsigned Msgs 5–7 never confirm alone; contradictory
  observations yield `AddressMismatch`, never last-write-wins.
- Relay roles (`i2pr-transport-ssu2::relay`): requester (bounded
  concurrent requests, response/tag/nonce correlation, HolePunch
  verification, transition to the normal handshake path),
  introducer (disabled by default; live-tag checks, per-peer/global
  quotas, 3x anti-amplification budget, replay idempotency,
  deterministic expiry, shutdown clears state), target (introducer-
  context validation, single HolePunch emission per intro with replay
  suppression). Exact `RelayRequestData` / `RelayAgreementOK`
  preimages; nonce-derived HolePunch connection IDs
  (`Dest = (nonce << 32) | nonce`, `Src = !Dest`); intro-key AEAD
  HolePunch and out-of-session PeerTest codecs.
- Introducer records (`i2pr-transport-ssu2::introducer`): one bounded
  owner (8 records, 3 published, deterministic oldest-expiry
  replacement, expiry withdrawal, failed-peer removal) feeding the
  Plan 159 publication builder's validated `Ssu2Introducer` inputs.
- Reachability consumption (`i2pr-transport::reachability`): typed
  `PeerTestOutcomeKind` (`Confirmed` supports; `AddressMismatch` /
  `FirewalledLikely` contradict; `Inconclusive` / `Rejected` neutral
  so inconclusive tests never flip state); relay success feeds
  `RelayFirewalledSignal` and never proves direct reachability.
- Session carriage (`session.rs`): full relay/peer-test blocks as
  typed `SessionEvent`s (no longer opaque) plus single-shot bounded
  `queue_relay_request/response/intro` and `queue_peer_test` controls.
- Runtime coordination (`i2pr-runtime::Ssu2PeerRelayService`): table
  ownership, per-source rate limits (8/sec, 1024 sources, cheap-drop
  before crypto), bounded signer registry, central expiry scheduler,
  `RelayFirewalledSignal` mirroring, validated-introducer selection,
  shutdown-to-baseline, and privacy-safe snapshots/counters.
  Introducer service stays disabled by default.

Only Ed25519 router signatures verify in this pass
(multi-algorithm interop is Plan 161 debt); RouterInfo signing-key
plumbing into the runtime is deferred (tests register keys
explicitly). Daemon `[ssu2]` activation and non-loopback dials stay
fail-closed.

## Plan 521 peer-test scope (2026-11-07)

The router can now run the **I2NP** peer test (message **231**) against a
peer it already holds a session with, and a **confirmed** exchange records
the router's **own** reachability. This is the router-level mechanism; the
transport's out-of-session three-party peer test of Plan 160 is a different
thing and is untouched.

The switch is `ssu2.peer_test`. It is **off** by default and refused unless
the SSU2 service itself runs.

The message is a probed identifier and an opaque probed timestamp; the
responder echoes both **unchanged** and sends the answer back to the
**authenticated** peer the test arrived from. The originator matches an echo
only when the identifier **and** the timestamp match an outstanding probe
**and** the answer came from the peer the probe was sent to. The probed
timestamp is drawn at random, so a peer cannot make its own probe look like
this router's echo.

The router's own reachability is the transport's business: the daemon hands
the runtime a sealed proof of a **matched** round trip, and the runtime
records it against the session the exchange travelled on. A timeout, an
unmatched echo, a peer mismatch and a refused probe record **nothing**.

**Not in scope for this router:** the stock-peer half. No stock router
implements an I2NP 231 responder at the router level — i2pd uses message
231 only for a garlic-carried tunnel test
(`libi2pd/TunnelPool.cpp:436`, `:493-501`), and Java I2P has no
`TunnelTestMessage` class at all.

## Plan 522 outbound keepalive scope (2026-11-08)

The transport can now hold an **outbound** session open with a
**keepalive**: a padding-only SSU2 data packet with the immediate-ACK flag
set, twenty bytes, carrying **no** I2NP message. It is the shape the pinned
i2pd 2.61.0 reference already sends (`libi2pd/SSU2Session.cpp:269`), and the
reference's receiver honours the immediate-ACK flag unconditionally
(`libi2pd/SSU2Session.cpp:1758`), as Java I2P 2.13.0's `PeerState2` does
(`router/java/src/net/i2p/router/transport/udp/PeerState2.java:628`).

No I2NP message type is added, no SSU2 block type is added, and the proto
crate is untouched. The interval is the transport's own constant (sixty
seconds) and the unanswered deadline is three intervals, which is the
specification's own timeout code (`libi2pd/SSU2Session.h:169`).

The keepalive is **outbound only**: the runtime passes the interval to an
outbound session and to nothing else, so an inbound session's lifetime is
unchanged. It is **off** unless the router's outbound peer-session pool is
on (`ssu2.peer_pool`), which is itself off by default.

**Not in scope for this router:** the **stock-peer** half, which needs Plan
493's authorized two-host topology, and the **dial scope** of the pool — the
transport's own dial target accepts a loopback endpoint or an RFC1918 IPv4
address, so a public deployment cannot use the pool today.

## Plan 523 introducer-form scope (2026-11-09)

Plan 523 corrects the SSU2 **introducer set** — the peers that will
introduce this router to others — to the specification's own form. The
tree implemented the **SSU 1** form; the specification says of
`ihost[N]`/`iport[N]`/`ikey[N]` that those options "are for SSU only and
are not used for SSU2", and the SSU2 tuple is:

- `ih[N]` — the introducer's **router hash**, I2P base64, 32 bytes;
- `iexp[N]` — the introducer's **expiry**, ASCII digits, seconds since the
  epoch, optional in the address table;
- `itag[N]` — the introducer's **relay tag**, `1..=2**32 - 1`.

An SSU2 address that publishes introducers omits `host` and `port`: the
specification forbids publishing them, and a peer resolves an introducer by
hash through the network database rather than by endpoint.

The scope is the **form**, everywhere this tree expresses one:

- the transport's address parser reads `ih`/`iexp`/`itag` and **refuses** the
  SSU 1 options in an SSU2 address rather than ignoring them;
- the transport's parser refuses an address that carries both a direct
  endpoint and introducers;
- the transport's publication builder renders the specification's form;
- the netdb gains a second qualification rule and a second builder for the
  introducer-only form, beside the untouched direct rule.

The **composition** — asking a peer for a relay tag, recording an
introducer, publishing the router's own introducer set, and advertising the
`C` capability — is **not** in scope and is a successor's subject. Nothing
is advertised: `router.version` stays `0.9.62` and the published RouterInfo
is unchanged.


## Plan 524 introducer-acquisition scope (2026-11-09)

Plan 523 corrected the SSU2 introducer set's **form**. Plan 524 gives the
router the **acquisition** half of the same composition: it learns that a
peer is an introducer, asks such a peer for a relay tag, and records the
answer as an authenticated introducer.

The condition is the reference's own
(`libi2pd/SSU2Session.cpp:753`):

```cpp
if (GetRouterStatus () == eRouterStatusFirewalled && m_Address->IsIntroducer ())
```

— the router is **firewalled** and the peer **advertises** the introducer
capability (`caps & eSSUIntroducer`, `libi2pd/RouterInfo.h:184`). The
pinned Java I2P 2.13.0 reads the same introducer marker from the address

The scope is the **acquisition**:

- the daemon reads the peer's advertised capability from its **validated**
  RouterInfo in the authoritative store, and parses the address with the

- the daemon asks **one** peer per cadence window, and only a peer it
  already holds a **session** with — the request rides the session and no

- the runtime records the tag that answers the router's **own** request as
  an authenticated introducer, and **refuses** a tag for a peer the router

The **publication** half — building the introducer-only address, choosing it
over the direct form, and signing it — is a successor's subject, and so is
the `C` capability this router publishes about **itself**. Nothing is
advertised: `router.version` stays `0.9.62` and the published RouterInfo is

Plan 524 gave the router the **acquisition** half of the SSU2 introducer
composition. Plan 525 gives it the **publication** half: the router
publishes the validated introducer set it learned, in the specification's

The reference publishes **one** SSU2 address whose shape depends on

bool isPublished = address.published && !address.host.is_unspecified () && address.port;

The **`C` capability** this router publishes about **itself** is a third,

## Plan 526 introducer-advertisement scope (2026-11-10)

Plan 525 gave the router the **publication** half of the SSU2 introducer
composition. Plan 526 gives it the **advertisement** half: the router
advertises the specification's Relay capability — the `"C"` letter — in its
**own** address.

The reference publishes the role letters on the **published** form only
(`libi2pd/RouterInfo.cpp:1350`-`:1373`), and its peer-side check demands an
endpoint for an introducer (`:1059`), so the `C` rides the **direct** form and
never the introducer-only one.

The scope is the **advertisement**:

- the runtime composes the capability in one place: the family letter, plus
  the role letter **only** while the introducer role is live;
- the runtime's install gate **refuses** a role-bearing record while the role
  is not live, so a stale letter cannot reach the wire;
- the netdb gains a **third** qualification rule and a **third** builder,
  beside the untouched direct and introducer rules; the third rule is exact,
  and the third builder carries no floodfill permit;
- the daemon matches on the **typed** published form and counts the three
  published forms under their own reasons.

The tree publishes the **combination** `"4C"` rather than the reference's
role-only `"C"`, because the tree's stricter rule requires the capability
string to name the address's own family. Both are inside the specification's
`[B,C,4,6]` alphabet, and both references parse a combination.

The `B` (peer-test) advertisement is out of scope. Nothing is advertised in the
inventory sense: `router.version` stays `0.9.62` and the inventory's
advertised count stays **zero**.

## Plan 527 reachability-contradiction scope (2026-11-10)

The SSU2 specification's reachability is a **claim** about the router's own
address, and a claim must be able to be **false**. Plan 527 gives the
router's reachability one owner and one reader, so a contradicting
observation reaches the product.

**What the tree now does.** The data-phase Address block carries a validated
endpoint, and the session keeps it instead of discarding it — **no codec,
block or option changes**. The runtime compares the observed endpoint with
the router's **own bound socket**: an agreement corroborates the router's
reachability and a disagreement **contradicts** it, because the router is
behind a NAT and must not publish a reachability claim it cannot honour. A
contradiction is never also a corroboration, so one observation is one fact.

**What the tree no longer does.** The peer-relay service keeps **no**
reachability tracker. It used to, and every contradicting signal was written
into it while the product read a different tracker — so the router's
reachability could never be contradicted in the running router. The service
now returns the typed facts it computes and the **runtime** records them, and
every typed peer-test outcome is recorded, not only the confirming one.

**What is unchanged.** The transport's reachability **model** is untouched:
the five signal kinds, the corroboration classes, the corroboration floor and
the state machine are exactly as they were. The router's SSU2 session
establishment, its peer test, its introducer role and its publication are
unchanged. No configuration key is added.

**What is not claimed.** The **requester** side of the SSU2 relay protocol,
which produces the relay-success indication in the field, stays unwired; the
surface's evidence is local, and the **stock-peer** half needs Plan 493's
authorized two-host topology.

## Plan 528 peer-test-verdict scope (2026-11-10)

The SSU2 specification states the peer-test result as a **table** over the
three messages Alice received, and one of its rows is FIREWALLED. Plan 528
makes the tree able to state that verdict and able to keep it.

**What the tree now does.** The specification's peer-test result table is
**transcribed** into the tree as data and pinned by a test, so the tree's
rule is checkable against the specification rather than only against prose.
The transport's reachability model separates the **contradiction** floor from
the **corroboration** floor: the corroboration floor stays at two, so
`Reachable` still needs three distinct supporting classes, and the
contradiction floor is one — the specification's own single-peer-test rule. A
**firewalled verdict** — a peer test that concludes the router is not directly
reachable — is first class and puts the router in `Firewalled`. The runtime
compares the observed address with the router's **own bound socket** and
records a disagreement as that same firewalled verdict, and the controlled
driver returns every verdict as a **fact**: its error arm keeps only the
genuinely failed cases.

**What the tree no longer does.** It no longer turns a disagreement into an
error. The controlled driver's outcome enum had exactly one variant,
`Confirmed`, and every other outcome became `ExchangeNotConfirmed` — so a
peer test that succeeded and concluded the router was behind NAT looked
exactly like a peer test that failed. The enum now carries the verdicts, and
the daemon's controlled activation still refuses anything that is not a
confirmation.

**What is unchanged.** No codec, block or option changes: the verdict rides
the messages the tree already sends. The transport's signal **vocabulary** and
its corroboration classes are untouched. No configuration key is added and no
default moves.

**What is not claimed.** The specification's "FIREWALLED or SYMNAT" row is
read **conservatively** as ambiguous — neither a confirmation nor a
firewalled verdict. The **production** SSU2 peer-test driver stays unbuilt,
and the delivery is confined to the **controlled loopback profile**: the
comparison is between two loopback addresses, so the contradiction is a
**qualification** claim. The **stock-peer** half needs Plan 493's authorized
two-host topology.

## Plan 529 observed-address scope (2026-11-10)

The SSU2 specification's Address block (type 13) carries "Alice's address,
sent to Alice by Bob, or Bob's address, sent to Bob by Alice" — the address
at which the **recipient** sees the **sender**. Plan 529 makes the tree
carry that value and read it back.

**What the tree now does.** The responder's Session Created and its Retry
carry the **observed source address** of the request they answer, taken from
the datagram's own header. The initiator's Session Request carries Alice's
view of Bob, and the responder reads it: the block is symmetric and the
reference reads it in both directions. The initiator reads the Address block
out of the decrypted Session Created payload and carries it on the
established session; the responder reads the Session Request's block and
carries it across the handshake transitions. The runtime compares the
observation with the router's **own bound socket**.

**What the tree no longer does.** It no longer publishes the responder's own
bound address as the initiator's address — the block's value was never the
right one — and it no longer decodes the Session Created's payload and
throws the Address block away. `ResponderConfig::local_address` is gone.

**What is unchanged.** No codec, block type, length or option changes: the
block type is 13, its length is 6 or 18, and its placement is exactly where
the tree already put it. Only the **value** changes, and it changes to what
the specification says it must be. The transport's reachability **model** —
its signal kinds, its corroboration classes and its state machine — is
untouched. No configuration key is added and no default moves.

**What is not claimed.** A missing or malformed Address block leaves the
session **established** and records nothing: the observation is evidence, not
a handshake requirement. The **Retry's** Address block is still **not** a
reachability observation — it is sealed outside the Noise transcript, so it
is a weaker fact, and the tree's Retry parser keeps discarding it. The
delivery is confined to the **controlled loopback profile**, the
**production** SSU2 peer-test driver and the **requester** side stay out of
scope, and the **stock-peer** half needs Plan 493's authorized two-host
topology.

## Plan 530 explicit-bind scope (2026-11-10)

The transport's reachability model says `Reachable` needs **three distinct
supporting classes**. Plan 530 supplies the third one: the router's own
configured bind.

**What the tree now does.** The runtime records the explicit-bind
corroboration class at **bind time**, because that is when the fact becomes
true. The recorder is private and lives in the runtime, which owns the
tracker and the sockets. It is gated on the **existing**
`explicit_bind_corroboration` opt-in — the one the daemon already maps to
`true` — so no configuration key is added and no default moves. It records a
family only when the runtime can **name** its own bound endpoint for it,
reusing the predicate `bound_endpoint` already applies, so a wildcard or a
port-zero bind names no address and records nothing. The signal carries only
the **family**, never a literal endpoint.

**What the tree no longer does.** It no longer leaves the explicit bind
class to the controlled floodfill activation alone. The narrow controlled
recorder and its call site stay byte-identical — they are Plan 283's
foundation, and the controlled activation's fail-closed refusal is not
weakened — but the class is now also earned in **ordinary** operation.

**What is unchanged.** The transport's reachability **model** — its signal
kinds, its corroboration classes, the corroboration floor of two and the
contradiction floor of one — is untouched, and `Reachable` still needs three
distinct classes. No codec, block type, length or option changes. No
configuration key is added and no default moves. The daemon records no
reachability signal of its own.

**What is not claimed.** The runtime's publication path stays
**loopback-only**, so the direct form the plan makes reachable is a
**controlled-loopback** claim, not a public-internet one. The peer test stays
behind the default-off `ssu2.peer_test` opt-in. The class expires with the
observation TTL and the plan adds no timer, so a router that binds once and
never observes a peer loses its evidence — the re-record is a follow-up, not
part of this plan. The **production** SSU2 peer-test driver and the
**requester** side stay out of scope, and the **stock-peer** half needs Plan
493's authorized two-host topology.

## Plan 531 relay-requester scope (2026-11-10)

The relay protocol has two halves. The **introducer** half — answering a relay
request and introducing the target — was already in the tree (Plans 499, 524
and 526). The **requester** half is what this plan adds.

**What the tree now does.** The router can reach a peer that publishes an
introducer set. The **policy** is the daemon's
(`crates/i2pr-daemon/src/relay_requester.rs`): it selects a target from the
**validated** RouterInfo store, resolves the introducer by hash, draws a fresh
nonzero nonce from the router's own randomness, signs the request with the
router's own identity, and starts it through the runtime's existing
`start_relay_request` seam. The **mechanics** stay in the runtime, which owns
the sockets, the session and the transport's verification. The transport's
relay state machines are **used, not edited** — the only transport change is a
`pub use RequesterState` re-export.

A hole punch travels **out of session**: it is sealed under the *receiver's*
introduction key and it names neither a session nor a peer hash, so it has its
own route and its own bounded handoff. A Relay Response is routed to the
requester's handoff **iff** it correlates with one of the router's own live
request nonces; every other response keeps travelling the introducer's handoff
exactly as before, and the existing drain is byte-identical.

**What the tree no longer does.** It no longer leaves the relay requester
without a producer, and it no longer leaves the transport's
`RelayFirewalledSignal` — class 4, contradicting — without a writer. A router
that reaches a peer only through a relay is **not** directly reachable, and
the tree now records that as a contradiction rather than as a corroboration.

**What is unchanged.** No codec, block type, length or option changes. The
transport's relay state machines and its reachability model are untouched, and
the corroboration floor is untouched. The existing `drain_relay_events` is
byte-identical. The daemon records no reachability signal of its own: it calls
the **runtime's** recorder, so the transport's own owner records the
contradiction.

**What is not claimed.** The **target** side's response emission has no
product wiring in this tree, so the lane completes that half over the
transport's own preimage. The delivery is confined to the **controlled
loopback profile**: the router's SSU2 dial target is loopback-only and the
private-LAN variant accepts only RFC1918 IPv4, so the requester can only reach
an introducer on a local or private network. That bound is Plan 431's. The
**stock-peer** half stays blocked on Plan 493's authorized two-host topology.
The **production** SSU2 peer-test driver stays unbuilt, and the `B`
advertisement and the `caps=f` advertisement stay with their owners.

## Plan 532 relay-target scope (2026-11-10)

The relay protocol has three roles. The **introducer** half — answering a relay
request and introducing the target — was already in the tree (Plans 490, 499
and 524). The **requester** half came with Plan 531. The **target** half — the
peer that is reached, and that **answers** — is what this plan adds.

**What the tree now does.** A router that is the peer an introducer named can
answer the Relay Intro it receives. The **policy** is the daemon's
(`crates/i2pr-daemon/src/relay_target.rs`): it reads the requester's
**validated** RouterInfo out of the authoritative store, takes the requester's
signing key and introduction key from that validated record through the
transport's strict `Ssu2RouterAddress::parse`, drives the runtime's existing
`on_target_relay_intro` seam so the transport's own target state machine is
used and not re-implemented, signs the accept with the router's **own** identity
key over the introducer-bound preimage, and hands the hole punch's pieces to
the runtime's outbound seam. The **mechanics** stay in the runtime, which owns
the sockets, the session, the bounded tables and the transport's verification.

**The introduction has its own bounded handoff.** A Relay Intro is addressed to
*this* router — the introducer forwarded it to the peer its tag named — so it
belongs to the target role and not to the introducer's. The runtime gives it a
**fourth** channel with the same ceiling as the relay handoff, and the session
loop routes the introduction to it **iff** the operator's `ssu2.relay_target`
opt-in is on.

**The hole punch is staged, never sessioned.** It is sealed under the
*requester's* introduction key and it travels out of session. It is built with
the transport's own codec and staged through the runtime's existing bounded
queue as control traffic, and its destination is checked against the **union**
of the two dial profiles the runtime offers, so the target role cannot widen
the router's reach beyond what the router already dials.

**What the tree no longer does.** It no longer leaves the transport's target
state machine without a producer, and it no longer routes a Relay Intro to the
introducer's handoff while the target's opt-in is on.

**What is unchanged.** No codec, block type, length or option changes. The
transport's relay state machines and its reachability model are untouched — the
plan changes no transport file at all — and both floors are unchanged. The
daemon writes no reachability signal of its own: a router that answers an
introduction is reachable **through the relay**, not directly, so the answer
gains no corroborating class.

**What is not claimed.** The introduction is routed to the target's handoff
**only while the opt-in is on**: with the opt-in off — the default — the
introduction keeps travelling the introducer's handoff exactly as before, and
the introducer owner refuses it as not its role. The transport's own requester
table requires the accept to be correlated **before** a hole punch is processed,
while the punch travels one hop and the accept two, so the requester owner has
no deferred-punch buffer. The delivery is confined to the **controlled loopback
profile**: the router's SSU2 dial target is loopback-only and the private-LAN
variant accepts only RFC1918 IPv4, so the target can only answer an
introduction for a requester on a local or private network. That bound is Plan
431's. The requester's **validated** RouterInfo must be in the authoritative
store. The **stock-peer** half stays blocked on Plan 493's authorized two-host
topology. The **production** SSU2 peer-test driver stays unbuilt, and the `B`
advertisement and the `caps=f` advertisement stay with their owners.

## Required MVP behavior

### Address publication and socket model

- Parse/publish current SSU2 RouterAddress options, static key, introducer/relay information and reachability fields.
- Use separate IPv4 and IPv6 socket/listener state where needed for correct address and migration handling.
- Keep observed external addresses and publication decisions outside the packet codec.
- Do not publish a directly reachable address until peer-test/observation policy supports it.

### Admission, tokens and handshake

Implement explicit initiator/responder states for:

- session request/created/confirmed messages;
- retry/address-validation token issuance and validation;
- fragmented RouterInfo in establishment where required;
- transcript/KDF/header protection and authenticated payloads;
- timestamp, network-ID, peer identity and source-address checks;
- replay/duplicate establishment handling.

Token validation must occur before avoidable expensive cryptographic work. Token keys require rotation, bounded overlap and restart semantics. Invalid/spoofed-source traffic must not create unbounded per-source state.

### Data phase

Implement:

- packet header parsing, obfuscation/protection and connection IDs;
- packet-number reconstruction and replay window;
- authenticated block parsing;
- ACK ranges/NACK or loss inference as specified;
- retransmission of I2NP fragments without promising ordered I2NP delivery;
- I2NP message fragmentation/reassembly with strict budgets;
- immediate-ACK and termination behavior;
- session key rotation/rekeying;
- idle timeout and clean teardown;
- duplicate I2NP suppression at the I2NP layer in addition to packet replay checks.

Loss recovery and congestion behavior must be bounded and stable under severe loss. Avoid one task or timer per packet.

### Relay and peer test

Implement current relay roles and messages required for ordinary firewalled-router operation:

- introducer advertisement/selection;
- relay request/response/introduction;
- signed data verification and freshness;
- per-peer/IP quotas and anti-amplification checks;
- peer testing for inbound reachability and address agreement;
- state transitions that cannot be confused across concurrent tests.

A relay or peer-test response must not cause address publication from a single unauthenticated observation.

### Migration/path validation

Support source-address changes only through specification-defined validation. Do not migrate an established peer merely because an authenticated-looking packet arrives from a new address without the required path challenge/response or equivalent state.

## Security and resource requirements

- Bound datagram size before parsing and drop impossible packets cheaply.
- Separate stateless/low-state prevalidation from allocated session state.
- Rate-limit token generation, Retry, relay and peer-test responses by source and globally.
- Prevent amplification by enforcing response-size and validation rules.
- Bound active sessions, pending handshakes, packet histories, ACK ranges, retransmissions and reassembly bytes.
- Reject packet-number replays and excessively old/future windows.
- Use constant-time authentication through reviewed crypto libraries.
- Avoid reflecting detailed parse/authentication failures.
- Release packet buffers and resource permits on cancellation, migration failure and timeout.

## Plan 533 relay-establishment scope (2026-11-11)

Plan 533 closes the last gap in the SSU2 relay exchange on this tree: the
requester now **establishes** the session with the peer it reached through a
relay, using the accept's token and the runtime's ordinary establishment path.

**The token.** The accept carries the target's own **establishment token**. The
token is issued by the target's responder table and bound to the requester's
**exact** source address, with the target's responder as the only authority on
it: one use, exact address, and a bounded lifetime. The initiator presents it
in its Session Request and the responder consumes it from the table it was
issued into. A token the target did not issue, a second presentation, and a
presentation from another address are each refused by the responder.

**The ordering.** The transport's requester table refuses a hole punch until
its accept has been correlated. The hole punch travels **one** hop and the
accept travels **two** — the introducer receives, verifies and forwards it — so
the punch reaches the requester first on any ordinary path. The requester holds
the punch until the accept lands and presents it again; the transport's rule is
unchanged and still enforced.

**The establishment.** The requester dials the target at the endpoint the
accept named, with the target's static and introduction keys read from the
target's **validated** RouterInfo, and the target is checked against the
**qualification profile** before the dial. The establishment is the ordinary
SSU2 handshake: no relay-specific session is created and the responder's
verification is never bypassed.

**What this tree does not do.** The delivery is confined to the controlled
loopback profile, the roles stay behind default-off operator opt-ins, and the
stock-peer half of the relay protocol needs the authorized two-host topology.

## Plan 534 relay-session-peer scope (2026-11-11)

Plan 533 closed the SSU2 relay exchange on this tree: the requester
**establishes** the session with the peer it reached through a relay. Plan 534
extends the scope from the session to the **route**: the router now builds a
tunnel toward that peer.

**The named build target.** The product's tunnel-build route draws its peer
from the peer-profile store's policy selection, so a peer the router had
deliberately reached through a relay was one candidate among every peer the
router knew. The deliberate reach is now honoured: the peer the router reached
becomes the route's **named** build target.

**The same floor.** A named target passes the **same** API-version floor every
drawn candidate passes, and the gate's verdict is carried faithfully. A peer
below the floor is refused and counted — it cannot complete the build, and a
build that cannot complete burns a tunnel slot and a coordinator lease. A named
target whose **validated** record the router does not hold is a **local**
condition and is counted as such, never as the peer's missing version.

**The observation.** It is a bounded, expiring **local** record that this
router reached a peer through a relay. It is **consumed** by the route that
used it and it **expires**, because a session that died while the router was
not looking must not be built toward. It writes nothing into the peer's record
and claims nothing about the peer's reachability.

**What this tree does not do.** The build goes through the **existing**
coordinator, so no second build path exists; the transport's relay state
machines and the reachability model are untouched; no configuration key is
added, and the table rides the requester's default-off opt-in. The delivery is
confined to the controlled loopback profile, and the stock-peer half of the
relay protocol needs the authorized two-host topology.

## Plan 535 explicit-bind-refresh scope (2026-11-11)

Plan 530's explicit-bind scope gave the router its **own** corroboration
class: the router records the sockets it has bound, and the transport's model
counts that class as one of the three distinct supporting classes `Reachable`
requires. The scope had a defect the plan itself recorded: the class **lapses**
with the observation TTL, because the transport's model holds every signal as
a timed observation, and nothing re-asserted the class.

Plan 535 closes that defect without touching the model. The transport's model
is right for a peer-sourced class — an observation of a peer says
something about the world at a moment, and it goes stale — but the
explicit bind says something about **this router's own socket**, and that does
not go stale while the socket is bound. The tree's own vocabulary already
carries the distinction: the signal is `LocalConfiguredBind`, not
`ObservedBind`. So the router **re-asserts** the fact the model holds, and the
fact's own lifetime is renewed by the owner of the fact.

**The rule.** `explicit_bind_refresh_due(recorded_at, now, observation_ttl)` is
public and pure. The re-assertion is due once the record has aged past
**half** the observation lifetime. Half is chosen so the re-assertion always
happens while the previous record is still live: a rule of "re-assert once
the record has expired" would be wrong, because the expiry poll runs on the
**read** paths, so a read between the record's expiry and the next
maintenance pass would find the class already gone. The rule **fails
closed**: a fact that was never asserted is due, and a zero lifetime is due
on every pass — a class that is re-asserted too often is harmless and a
class that lapses is not.

**The lifetime has one owner.** The runtime does not keep its own number for
the observation lifetime. It reads the tracker's own policy back
(`state.reachability.policy().observation_ttl()`), so the expiry rule has one
owner and the runtime cannot drift from it. The runtime's configuration
parameter (`Ssu2RuntimeReachability`) exists so the *policy* can be
configured and the behaviour can be proved; its production default is the
transport's own `DEFAULT_OBSERVATION_TTL`, and the daemon's mapping names
that default.

**The re-assertion rides the existing maintenance.** The runtime already
wakes its socket loop at least every `scheduler_poll_max` and runs its
maintenance pass on every wake. The re-assertion is one step of that pass.
**No new timer** is introduced.

**The re-assertion is a fact about this router.** It touches the router's own
reachability tracker, writes no peer profile, claims no corroborating class
for any peer, and records no reachability signal about anything but this
router's own socket. The families the router's own sockets can be named for
are captured at bind time, because the runtime binds once and does not
rebind — so the re-assertion needs neither the sockets lock nor a
second clock, and the runtime's lock order (sockets — state) is never
inverted.

**The transport is untouched.** The signal vocabulary, the corroboration
classes, the floors, the states and the expiry semantics are unchanged, and
the tracker gains no method: the re-assertion *records* through the method
the transport already offers.

**No configuration key is added.** The daemon's configuration surface is
unchanged, and the daemon's mapping names the runtime's own default policy.
Nothing is advertised: `router.version` stays `0.9.62` and the inventory's
advertised count stays **zero**. The delivery is confined to the controlled
loopback profile, and the stock-peer half needs Plan 493's authorized
two-host topology.

## Plan 536 relay-target-answer-lock scope (2026-11-11)

Plan 532 built the relay **target** role. Plan 536 does not change what the
role **does**; it changes **where the answer is produced** and it removes a
**silent skip**.

**The answer is produced outside the router's NetDB lock.** The composition
root drained the target's handoff inside the bootstrap's mutex — the router's
NetDB lock — for the whole pass, and the pass is bounded at
`MAX_RELAY_DRAIN_PER_PASS = 16` answers. Each answer parses an address, signs
an accept and stages it on a session, and all of it happened while the caller
still held the lock. The same mutex is taken by the router's NetDB discovery
tick, by the requester's outbound step, by the RouterInfo publication tick, by
the peer reconcile and by the peer pool.

The material read is now taken under a **short, bounded** lock — one named
peer, one strict address parse, two derived values — and the guard is
**released before the read returns**. The accept is therefore signed and
staged with **no lock held**, exactly as Plan 533's establishment task already
does for the same store. The **wire** is unchanged: the introduction's bytes,
the accept's bytes, the hole punch and the transport's target table are
exactly what the tree already produced.

**The drain is never skipped silently.** The drain used to be gated on the
daemon **holding** a `Bootstrap`: a router that did not hold one did not
drain, did not refuse and did not count, so an introduction that arrived and
could not be answered left no trace. The drain now runs whenever the target
role exists, and a missing store — or a poisoned lock — is a **typed, counted
refusal** (`StoreUnavailable`, counted under `refusals_store_unavailable`).
The refusal is a fact about **this router**, never about the requester, and
it is never written into the requester's profile.

**The read stays read-only.** One named peer is read, one address is parsed
with the transport's strict parser, two values are derived, and nothing is
mutated and no peer profile is written.

**What is unchanged.** The target role's semantics — the accept's signature
preimage, the hole punch, the dial profile, the transport's target table and
the transport's refusal order — are untouched, and Plan 532's lane and guard
stay **byte-identical**. No codec, block type, length or option changes, and
no transport file changes at all.

**What is not claimed.** The plan adds **no** store, **no** lock, **no** owner,
**no** configuration key, **no** task, **no** timer, **no** listener and **no**
socket. The router's validated store is still the bootstrap's store, so
separating the router's NetDB from the bootstrap's lifetime remains a
successor's work. The delivery stays confined to the **controlled loopback
profile** — Plan 431's bound — the **production** SSU2 peer-test driver stays
unbuilt, the `B` advertisement and the `caps=f` advertisement stay with their
owners, and the **stock-peer** half needs Plan 493's authorized two-host
topology.
