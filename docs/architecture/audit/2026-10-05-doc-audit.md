  variants, `ResourceError`'s 10, and the Mutex-not-RwLock

New source that the deep dives had to absorb:

- `crates/i2pr-service-tunnels/src/outproxy.rs` (1 724 lines) — the
  runtime-neutral outproxy provider **policy**. `OutproxyEndpoint::parse`
  proves a target is an I2P destination, and the path may open exactly
  one kind of route: an I2P Streaming connection, never a direct
  clearnet socket.
- `crates/i2pr-daemon/src/outproxy_route.rs` (976 lines) — the
  socket-owning route **owner**, the daemon half of the same seam.
- `scripts/check-service-tunnel-boundaries.sh` **rules 9–11** —
  require both outproxy files to exist; fail if either names a
  clearnet socket/resolver/TLS client (`TcpStream|TcpListener|
  UdpSocket|to_socket_addrs|lookup_host|TcpSocket|openssl|
  native_tls|reqwest|hyper`) — with `std::net::IpAddr` deliberately
  *not* matched, since parsing an address is how the target grammar
  refuses IP literals; fail if either loads a plugin or spawns a
  process (`libloading|dlopen|Library::new|Command::new|
  std::process`); and **rule 10 is a positive control** requiring
  `service_tunnels_http.rs` to still contain `TcpStream|TcpListener`,
  so the guard cannot silently go vacuous.
- `specs/references/proposal-170-outproxy-provider.md` (new).
- Plans 341 (restart-safe outbound proxy secret owner), 342 (daemon
  outproxy route owner), 343 (outproxy provider policy and route
  owner).

**Status discipline.** Plan 343's token is
`passed-outproxy-provider-policy-and-route-owner-with-no-reachable-request-path`
— the policy and the route owner landed, but there is **no reachable
request path**, so this is not a working outproxy. The token is
independently corroborated in source: `open_via_outproxy` in
`crates/i2pr-daemon/src/outproxy_route.rs` has **zero callers**
(verified by grep across `crates/**/*.rs`, excluding its own
definition), which is exactly what "no reachable request path" means.
Plan 327 remains **blocked**
(`blocked-prop170-outproxy-provider-needs-routed-provider-and-secret-owner`),
with a dated 2026-10-05 correction narrowing it from two blockers to
one after Plan 341 removed the secret-owner gap. The docs therefore
replace a flat "no clearnet outproxy" non-goal with the precise
statement: policy and route owner exist and are enforced; there is no
reachable request path and no direct clearnet fallback.

Note that `plans/registry.md:39` is only *half* stale here: its claim
that Plan 327 is blocked is correct, while its claims about Plans 322

The same upstream batch fixed a comment/code mismatch in
`open_via_outproxy`: the comment claimed the last attempt's reason was

counted, so "the outproxy rejected the credential N times" survives as
an operator-visible diagnosis. That is the right fix — a comment
overstating what the code does is a defect in a security-relevant path
precisely because the discarded value was the diagnosis an operator
would need.
