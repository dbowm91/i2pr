# Plan 089: conditional manual isolated i2pd probe fallback

## Status and activation

- Status: planned, conditional only.
- Parent roadmap: Plan 085.
- May be activated only when Plan 086 records `manual-isolated-fallback-required`, or Plan 088 records the same decision after a previously working direct placement becomes unavailable before TCP.
- Must not be activated for a protocol rejection, protocol timeout after TCP, ambiguous wire-stage behavior, or evidence-finalization failure.
- Reuses the Plan 087 and Plan 088 runners and compact record schemas unchanged.
- Plan type: one-shot isolated execution placement, not a new interoperability architecture.

## Objective

Provide one executable Ubuntu lane when direct host loopback cannot start or bind for a demonstrated placement reason.

The preferred runtime is one rootful Linux container with:

```text
--network none
loopback enabled inside the container
both i2pr and i2pd processes inside the same container
no public interface or default route
prepared source/build artifacts available locally
one writable run root
```

The lane must support both existing role assignments:

```text
i2pr initiator -> i2pd responder
i2pd initiator -> i2pr responder
```

It must not duplicate protocol orchestration, schemas, event parsing, or evidence logic.

## Allowed hosting mechanisms

Choose the first available mechanism:

1. an existing authorized Ubuntu build host with an accessible rootful Docker-compatible daemon;
2. a manually triggered GitHub Actions Ubuntu job using the runner's existing Docker daemon;
3. another manually operated disposable Ubuntu VM with rootful Docker.

The mechanism must be manually invoked. Do not add `push`, `pull_request`, schedule, release, or recurring triggers.

## Build and execution separation

The runtime container uses `--network none`, so all dependencies and binaries must be prepared before execution.

Preparation phase may:

- check out the exact source commit;
- restore or build Rust artifacts;
- restore or build the pinned i2pd 2.60.0 instrumented and control drivers;
- verify source locks and binary digests;
- build a local execution image or assemble a local artifact directory.

Execution phase must:

- start one container with `--network none`;
- verify only loopback exists and no default route is present;
- enable loopback inside the container when required;
- run both peer processes inside that container;
- write compact results to the mounted writable run root;
- stop and remove the container;
- export only sanitized compact records and bounded logs.

Do not download, clone, install packages, contact registries, or resolve DNS during the execution phase.

## Container contract

Recommended shape:

```bash
docker run --rm \
  --network none \
  --read-only \
  --tmpfs /tmp:rw,nosuid,nodev,noexec,size=256m \
  --mount type=bind,src=<artifact-root>,dst=/opt/i2pr-artifacts,readonly \
  --mount type=bind,src=<run-root>,dst=/work/run \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  <local-image-digest> \
  <probe-entrypoint>
```

Adjust only where the exact i2pd driver needs a narrowly documented filesystem capability. Do not add `--privileged`, host networking, device mounts, or broad capabilities.

The container may need the ability to bring its loopback device up. Prefer image/daemon defaults where loopback is already up. When a capability is required, add the minimum specific capability during an isolated preflight and document it; do not use `--privileged`.

## Required preflight

Before protocol execution, prove inside the container:

```text
hostname and source commit recorded
network interface inventory contains loopback only
no default route exists
DNS resolution is not required
artifact digests match the frozen manifest
127.0.0.1 bind succeeds
both test binaries execute
run root is writable
artifact root is read-only
container teardown removes the owned runtime
```

Allowed preflight result tokens:

```text
manual-isolated-fallback-ready
manual-isolated-fallback-unavailable
artifact-drift
container-boundary-invalid
```

## Runner integration

The Plan 087 and Plan 088 entry points must accept a placement record generated by this plan.

Required placement metadata:

```text
topology_kind = manual-isolated-container-loopback
development_only = true
release_qualified = false
isolation_qualified = development-runtime-only
public_network_blocked = true
container_runtime
container_image_digest
artifact_manifest_sha256
source_commit
reference_revision
preflight_record_sha256
```

This is stronger isolation than Plan 086 direct host loopback but remains development evidence. It does not replace the final Plan 073 Java/release qualification gate.

Do not fork `plan083_runner.py` or `plan084_runner.py`. The container entrypoint must invoke the same runner functions or thin CLI used by Plans 087 and 088.

## Manual GitHub Actions option

A workflow is permitted only when all are true:

- trigger is `workflow_dispatch` only;
- no secrets beyond ordinary repository checkout are required;
- it does not publish images, releases, packages, or attestations;
- it builds or restores the exact pinned artifacts before the offline runtime phase;
- it runs one requested direction or both explicitly selected directions;
- it uploads only compact records and sanitized bounded logs;
- retention is short and documented;
- it cannot run automatically on commits or pull requests.

Prefer a small workflow wrapping committed scripts. Do not encode the harness logic in YAML.

## Direction execution

### Forward

After preflight, invoke the exact Plan 087 runner using literal `127.0.0.1` inside the container.

Preserve the Plan 087 stage and correction policy. A protocol failure after TCP returns to Plan 087, not Plan 089.

### Reverse

Invoke the exact Plan 088 runner only after Plan 087 passes.

Preserve the Plan 088 decision vocabulary. A reverse protocol failure returns to Plan 088, not Plan 089.

## Acceptance criteria

Plan 089 closes as `manual-isolated-fallback-ready` only when:

- the activation token from Plan 086 or 088 is valid;
- exact source and artifact digests are frozen before runtime;
- one `--network none` container starts with loopback only and no default route;
- no dependency access occurs during runtime;
- the exact Plan 087/088 runner entry point executes inside the container;
- artifacts are mounted read-only and the run root is bounded/writable;
- container and child cleanup are complete;
- a sanitized preflight/placement record is produced;
- no recurring CI trigger exists;
- the next active plan returns to Plan 087 or Plan 088 rather than creating another plan sequence.

Plan 089 may close as unavailable only when:

- no allowed rootful container runtime is accessible on an authorized host;
- the condition is recorded precisely;
- no protocol result is claimed;
- Plan 087/088 remain execution-pending.

## Stop rules

Stop when:

- activation came from a protocol-stage failure rather than placement failure;
- the runtime requires host networking or `--privileged`;
- the execution phase requires internet access;
- artifact digests drift after preparation;
- the proposed workflow gains automatic triggers;
- harness logic is being duplicated in shell or YAML;
- work expands into release publication, Java qualification, performance, or broad CI.

## Non-goals

Plan 089 does not:

- become the default local development path;
- replace Plan 087 or Plan 088;
- diagnose or fix protocol behavior;
- establish final release qualification;
- publish artifacts;
- add recurring CI;
- run Java or Emissary;
- create a generalized container test framework.

## Small-model execution guidance

1. Verify the exact activation token.
2. Prepare all artifacts before runtime.
3. Start one `--network none` container and run preflight only.
4. Write the placement record.
5. Invoke the existing Plan 087 or Plan 088 command unchanged.
6. Export compact results and remove the container.
7. Stop; protocol correction belongs to the direction plan.
