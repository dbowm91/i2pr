# Plan 186 — M6 mixed-router RouterInfo NetDB lookup and publication

Status: **blocked until Plan 185 passes**.

## 1. Goal

Drive the existing NetDB state machines over the real Plan 185 exploratory tunnel pair against exact-pinned i2pd. Prove RouterInfo lookup and publication through tunnel paths, not direct transport, and remove remaining placeholder live-store composition from the daemon NetDB seam.

No destination LeaseSet2/Streaming claim belongs here.

## 2. Required existing components

Reuse:

- `i2pr-netdb` RouterInfo store, lookup engine, routing-key/floodfill selection, validation, and publication state machines;
- `i2pr-daemon::netdb_seam`;
- `i2pr-daemon::outbound_lookup`;
- `i2pr-daemon::inbound_dispatch`;
- Plan 185 `ExploratoryPool` / `DataPlaneRegistry` paths;
- Plan 184 authenticated router-I2NP dispatcher and SSU2 RouterDelivery.

Do not add a second lookup engine, direct-transport NetDB shortcut, or test-only reply injection for counted rows.

## 3. Authoritative RouterInfo store

Audit `NetDbSeam` and remove live use of placeholder/empty RouterInfo stores where they prevent real floodfill selection. The daemon must expose one bounded authoritative RouterInfo store populated only by validated signed RouterInfo records.

For the controlled lane, bootstrap that store with exact signed RouterInfo material for the reference router. The bootstrap may come from the exact-pinned reference datadir/harness output, but must traverse the same parser/signature/freshness validation used for ordinary records before becoming eligible.

No public reseed is required or permitted for green evidence.

## 5. RouterInfo lookup trajectory

Required counted trajectory:

```text
i2pr lookup request
 -> real inbound exploratory reply path selected
 -> real outbound exploratory path selected
 -> existing LookupAction::SendDatabaseLookup
 -> existing outbound tunnel composition
 -> TunnelData over Plan 185 path
 -> i2pd floodfill
 -> reply routed to i2pr inbound exploratory tunnel
 -> TunnelData recovery
 -> inbound_dispatch / NetDbSeam
 -> signed RouterInfo validation
 -> authoritative RouterInfo store
 -> terminal lookup success
```

The target should be a deterministic RouterInfo present in the controlled dataset; it may be the reference router or another exact fixture only if the request still traverses the reference floodfill and real tunnels.

Evidence must prove direct SSU2 `DatabaseLookup` was not substituted for tunnel dispatch.

## 6. Publication trajectory

Publish a fresh i2pr RouterInfo through the existing publication state machine and real outbound exploratory tunnel. Verify acceptance/acknowledgement using protocol-correct DeliveryStatus or observable reference-state evidence.

Requirements:

- signed RouterInfo is generated by normal i2pr identity/publication code;
- no test edits to the serialized record;
- publication uses the existing floodfill selection/routing key logic;
- success requires protocol-derived acknowledgement/observation, not process exit alone;
- duplicate/expired/invalid publication failure remains bounded.

Do not broadly advertise i2pr on a public network; this is private controlled publication only.

## 7. Lookup retries and search replies

Exercise the existing bounded handling for `DatabaseSearchReply` / alternate floodfill candidates. In the one-reference topology, no-candidate/peer-exhausted behavior must terminate honestly rather than spin.

Test at least:

- successful DatabaseStore response;
- mismatched key/store rejected;
- stale/invalid RouterInfo rejected;
- DatabaseSearchReply with unknown peers does not cause unbounded work;
- lookup deadline and cancellation;
- duplicate response;
- malformed recovered I2NP;
- reference unavailable after tunnel establishment.

## 8. Resource/lifecycle rules

Bound:

- concurrent lookups;
- candidate count;
- pending publication acknowledgements;
- retained reply paths;
- RouterInfo store entries/bytes;
- retries/deadlines.

Tunnel loss during a lookup must return a typed retry/failure and may request replacement through Plan 185 policy; it must not silently fall back to direct transport.

## 9. Acceptance criteria

Plan 186 passes only when:

1. the live daemon NetDB seam uses the authoritative bounded RouterInfo store for real candidate selection;
2. exact-pinned i2pd acts as the controlled floodfill without public reseed/network dependence;
3. a RouterInfo DatabaseLookup traverses i2pr outbound exploratory TunnelData and the reply traverses i2pr inbound exploratory TunnelData;
4. the returned signed RouterInfo is validated and installed through the ordinary store;
5. a normal i2pr RouterInfo publication traverses the outbound tunnel and obtains protocol-derived success evidence;
6. direct SSU2 NetDB delivery is not counted as lookup/publication success;
7. search-reply, mismatch, stale, malformed, duplicate, timeout, and cancellation paths are bounded;
8. tunnel failure does not bypass exploratory-path requirements;
9. Plan 185 liveness remains green during NetDB activity;
10. prior M8/M9/M10 local regressions and full exact-head CI pass;
11. `plans/186-status.md` advances `next_executable_plan = 187`.

## 10. Stop conditions

Stop and write a narrow corrective if the reference floodfill behavior exposes a protocol mismatch in the existing NetDB encoding/validation or if the only route to success is direct transport. Preserve captured sanitized I2NP type/length/hash/status facts; never log full secret material.
