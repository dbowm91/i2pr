# Plan 142 — SAM 3.1 encoding and private-destination compatibility correction

Status: **next executable implementation plan** under Plan 141.

Depends on: Plan 141 corrective roadmap; Plan 137 loopback/session lifecycle remains usable.

## 1. Goal

Correct the SAM wire representation defect introduced during Plan 136 and replace circular private-destination evidence with independent compatibility evidence.

This pass owns:

1. SAM/I2P Base64 alphabet and padding behavior;
2. `PUB`, `PRIV`, full-Destination, and naming encoding consistency;
3. exact `DEST GENERATE SIGNATURE_TYPE=7` representation;
4. exact `SESSION CREATE DESTINATION=<PRIV>` import compatibility;
5. independent evidence for the ordinary Ed25519 destination/private-key-file representation;
6. correction of the inaccurate Plan 136 provenance/support documentation.

This pass does **not** implement the missing same-socket raw STREAM bridge. That is Plan 143.

## 2. Protocol facts that must not be re-litigated

The current official SAM v3 specification states under `BASE 64 Notes`:

```text
Base 64 encoding must use the I2P standard Base 64 alphabet
A-Z, a-z, 0-9, -, ~
```

Reference:

- https://www.i2p.net/en/docs/api/samv3/

The current `crates/i2pr-api/src/sam/base64.rs` uses RFC 4648 `+/`; this is wrong for SAM fields.

The fix must not be framed as permissive compatibility with one client. The canonical SAM output from i2pr must use the I2P alphabet.

## 3. Mandatory reference reconciliation before code changes

Before changing the private-destination layout, inspect and record current behavior from all of:

1. official SAM v3 specification;
2. official common-structures/private-key-file documentation;
3. Java I2P `net.i2p.data.Base64` behavior;
4. Java I2P `PrivateKeyFile` / session private-key serialization behavior;
5. at least one independent SAM client/implementation that handles `PUB`/`PRIV` (for example `i2plib`, libsam3, i2pd tooling, or another viable maintained client).

Update `specs/references/sam31-private-destination.md` so it distinguishes clearly between:

- normative SAM wire alphabet;
- historical minimum-size prose in the SAM specification;
- key-certificate-aware type-specific private-key lengths in current implementations;
- the exact representation i2pr chooses for its supported signing/encryption profile;
- what is proven by reference artifacts versus inferred from i2pr internals.

Do not preserve a statement merely because it was written by Plan 136.

## 4. I2P Base64 codec correction

Replace the current RFC-4648-only SAM codec with an explicit SAM/I2P Base64 codec.

### 4.1 Canonical alphabet

Canonical output must map the last two sextets as:

```text
62 -> '-'
63 -> '~'
```

not:

```text
62 -> '+'
63 -> '/'
```

### 4.2 Padding

Do not guess padding policy from RFC 4648. Verify the exact current Java I2P/SAM behavior for non-multiple-of-three lengths and freeze it in tests.

The implementation must have one documented canonical output policy. If reference implementations accept more than one input spelling, distinguish:

- **canonical encoder** — emits exactly the I2P form;
- **decoder compatibility policy** — accepts only representations demonstrated interoperable and safe.

Do not emit standard `+/` Base64 from SAM replies.

### 4.3 Bounds

Preserve or improve:

- pre-allocation encoded/decoded length checks;
- invalid-character rejection;
- padding-position validation;
- no whitespace folding;
- no trailing garbage;
- full consumption;
- no quadratic conversion.

### 4.4 Scope of replacement

Audit every SAM field that carries Destination/private-destination text and route it through the same corrected codec:

- `DEST REPLY PUB=`;
- `DEST REPLY PRIV=`;
- `SESSION CREATE DESTINATION=<private>`;
- `SESSION STATUS DESTINATION=` if emitted;
- `STREAM CONNECT DESTINATION=<public>`;
- ACCEPT/FORWARD peer-Destination lines;
- `NAMING REPLY VALUE=`;
- locally cached public Destination text in the SAM session registry;
- test fixtures/transcripts.

Do not fix only `PRIV` while leaving `PUB` or STREAM targets on the wrong alphabet.

## 5. PrivateKeyFile representation: prove before changing

The current `SamPrivateDestination` uses:

```text
Destination (391)
+ type-4 private key (32)
+ type-7 signing seed (32)
= 455 bytes
```

This may be a valid key-certificate-aware private-key-file representation, but existing evidence is insufficient.

### 5.1 Required independent artifact

Obtain at least one artifact not generated by i2pr code. Preferred order:

1. Java I2P reference implementation generated with Ed25519 signing and the encryption profile being claimed by i2pr;
2. i2pd/reference SAM-generated private destination with a compatible profile;
3. a maintained independent SAM library artifact whose provenance can be pinned and whose representation is known to match a reference router.

Record:

- source implementation and version/commit;
- exact generation command/API;
- signing/encryption types;
- binary lengths;
- public Destination hash;
- Base64 spelling policy;
- whether the private-key field is type-specific, legacy padded, zero/random, or otherwise transformed.

Do **not** commit a live/private production identity. Use a deterministic or throwaway test identity created only for this fixture.

### 5.2 Bidirectional proof

Required proof:

```text
independent/reference PRIV -> i2pr decode/import -> identical public Destination

i2pr generated PRIV -> independent/reference decode/session parser -> identical public Destination
```

If the external tool only exposes one direction, use a second independent method for the other direction.

### 5.3 Stop condition

If the reference representation cannot be reconciled with `DestinationIdentity` without changing destination encryption-key semantics or identity construction, stop Plan 142 and record the exact discrepancy. Do not silently add a second private-destination format.

## 6. Secret ownership correction

Preserve the improvements made during Plan 140:

- `SamPrivateDestination` non-`Clone`;
- redacted `Debug`;
- zeroizing owned buffer;
- consuming identity reconstruction.

Audit the currently public `private_bytes()` and `DestinationIdentity::signing_seed_bytes()` seams. If either is broader than necessary, narrow visibility or replace it with an owned serialization method while keeping tests possible.

Preferred direction:

```text
DestinationIdentity
  -> explicit SAM private-destination serialization operation
  -> owned Zeroizing buffer
```

rather than unrelated crates borrowing raw private keys indefinitely.

No private `PRIV` value may appear in normal tracing output, panic messages, or committed transcripts.

## 7. `DEST GENERATE` behavior

For the M7 declared profile:

- support `SIGNATURE_TYPE=7`;
- generate with `OsRng`/injected cryptographic RNG on production paths;
- output canonical I2P Base64 `PUB` and `PRIV`;
- re-import `PRIV` into an exact-identical Destination;
- reject unsupported signature types explicitly;
- do not silently default to DSA if DSA is not implemented.

The `PUB` value returned by DEST GENERATE must be immediately usable as a `STREAM CONNECT DESTINATION=` target by a maintained independent SAM client.

The `PRIV` value must be immediately usable by `SESSION CREATE STYLE=STREAM ... DESTINATION=<PRIV>` through both i2pr and the selected independent reference path.

## 8. Parser compatibility

Because I2P Base64 may contain `=` padding depending on verified reference behavior, ensure token parsing treats the first `=` as the option key/value delimiter and preserves all subsequent `=` characters in the value.

Add regression tests for:

- public Destination containing `-`;
- public Destination containing `~`;
- private Destination containing both;
- any canonical padding suffix established by reference behavior;
- no value uppercasing;
- no URL decoding;
- quoted/unquoted values where permitted.

## 9. Independent-client smoke gate for Plan 142

Plan 142 does not require STREAM bytes yet, but it does require at least one independent client/reference implementation to reach the real i2pr listener and prove the representation layer.

Minimum localhost trajectory:

```text
HELLO VERSION MIN=3.1 MAX=3.1
DEST GENERATE SIGNATURE_TYPE=7
SESSION CREATE STYLE=STREAM ID=fixture DESTINATION=<returned PRIV>
NAMING LOOKUP NAME=ME (if supported by the chosen client/transcript)
```

The independent side must accept the server's public/private spelling. A pure i2pr Rust transcript test alone is insufficient for this criterion.

If `i2plib` is retained, pin its exact revision. If another maintained client is easier to execute, switch rather than patching around a stale toolchain.

## 10. Tests

### 10.1 Base64 unit vectors

Freeze vectors that force sextet values 62 and 63 so accidental regression to `+/` is detected.

Required assertions:

- encoder emits `-` and `~` where reference does;
- encoder never emits `+` or `/` in canonical SAM output;
- decoder accepts canonical reference strings;
- malformed/mixed alphabets follow an explicit documented policy;
- padding behavior exactly matches frozen reference vectors.

### 10.2 Private destination

- deterministic i2pr type-7 generation;
- reference-generated fixture import;
- cross-implementation public Destination/hash equality;
- truncation at every structural boundary;
- one-byte trailing garbage;
- wrong signing type;
- wrong encryption type/profile;
- public/private mismatch;
- corrupted signing private key;
- corrupted encryption private key where the profile makes it meaningful;
- secret redaction.

### 10.3 Real listener

Through `127.0.0.1:0`:

- DEST GENERATE output uses canonical alphabet;
- generated PRIV creates a session;
- imported independent PRIV creates the same public Destination;
- public Destination can be used in naming normalization;
- disconnect releases the session.

## 13. Acceptance criteria

Plan 142 closes only when all are true:

1. canonical SAM Base64 uses the I2P `-`/`~` alphabet;
2. padding behavior is verified against reference implementation behavior and frozen in tests;
3. all SAM Destination/private-Destination fields use one corrected codec/policy;
4. standard `+/` output is no longer emitted by i2pr SAM;
5. `DEST GENERATE SIGNATURE_TYPE=7` round-trips through i2pr session creation;
6. at least one independently generated private-destination fixture imports into i2pr with exact public Destination/hash equality;
7. i2pr-generated material is accepted/decoded by at least one independent/reference implementation;
8. the exact type-7/private-key-file binary layout is documented based on independent evidence, not circular inference;
9. unsupported/offline/private-key layouts fail explicitly unless intentionally supported;
10. secret ownership/redaction/zeroization remains intact or is improved;
11. an independent localhost client/reference smoke trajectory reaches the real listener and successfully uses generated/imported destination material;
12. no raw STREAM bridge acceptance is claimed;
13. all global validation gates pass;
