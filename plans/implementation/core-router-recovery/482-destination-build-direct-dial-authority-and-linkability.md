# Plan 482 — Destination-scoped dial authority and inbound-gateway linkability guard

**Status:** registered / ready, P0 privacy architecture contract, parallel to Plan 481; consumed by active Plan 478 before normal client-product closure (2026-10-13). **Owner:** i2pr-daemon Destination tunnel provisioning/session-establishment policy and shared router-delivery dial authorization; route wire composition and SAM/LS2 integration remain in Plan 478. **Baseline:** `work/plans-477-480-router-recovery@9ac340af198da614d7f03d0d69ecfdd0a0d66aa7`. **Canonical:** `GUARDRAILS.md` §§2,3,7,8; `docs/adr/0030-destination-linkability-domains-service-lifecycle-and-i2pd-streaming.md`; `plans/subsystems/anonymity-roadmap.md`; `specs/CONFORMANCE.md`; `specs/support.toml`. **New-owner justification:** a normal Destination's capability to *cause a direct transport session* is a privacy policy distinct from the Plan 478 tunnel-data routing algorithm. A durable dial-authority boundary is required across initial builds, replacements and future transport fallback—not simply one conditional change in the build composer.

## Source-level privacy discrepancy

At PR #46 head, `crates/i2pr-daemon/src/service_product.rs::provision_all_service_router_material` establishes both `outbound_peers[0]` **and `inbound_peers[0]`** using `ensure_selected_peer_session(..., ssu2_handle, selected_hash, ...)` before submitting the builds. The latter function selects a validated SSU2 RouterInfo, calls `Ssu2DaemonHandle::dial`, and may create a new direct authenticated router-level connection to the **inbound gateway** purely because a local Destination selected that gateway. The same service path now submits the inbound ShortTunnelBuild through `submit_destination_via_outbound_tunnel`, routing TunnelData to the established outbound tunnel's first hop. Therefore, the source-level "no direct *build message* to inbound gateway" property does **not** imply the stronger "no Destination-triggered direct session to inbound gateway" property. Direct session establishment may reveal a router-level temporal relationship; **no observed deanonymization is asserted** and routine router traffic may legitimately have direct sessions to many peers.

`rebuild_destination_tunnel` and all replenishment callers also invoke `ensure_selected_peer_session` on `selected[0]` before choosing outbound routing, so startup-only fixes would leave the same policy gap on rotation. `RouterDeliveryService::deliver_with_transport` can request a background NTCP2 dial on total route miss; the policy must avoid an indirect route-miss-triggered direct connection to an inbound gateway. The originator's return path and i2pd's stock reply routing must be source-verified; forbidding a direct **initiated** session is not permission to reject authenticated inbound sessions legitimately needed for replies.

## Classification and policy ownership

**Capability:** normal service Destination tunnel creation, renewal and failover do not initiate an unnecessary direct router transport session to their chosen inbound gateway solely to create the Destination's tunnel, while allowing valid router-wide background routing and necessary authenticated return traffic. **Infrastructure:** typed per-operation dial/route authority, purpose-specific direct-versus-tunneled delivery selection and privacy-safe denial/fallback. **Invariant:** router and Destination identities remain distinct; no destination-selected first-hop direct-dial bypass, fallback, second service-specific router runtime, or unqualified direct inbound-build bootstrap; do not block general-purpose router traffic because an identity coincides with a Destination path. No claims of cryptographic anonymity solely from no-dial tests. **Polish:** precise source-owned audit categories for bootstrap and policy denial, without stable peer labels.

## Ordered implementation pass

1. **Inventory all call paths and exceptions.** Trace `ensure_selected_peer_session`, `rebuild_destination_tunnel`, `provision_all_service_router_material`, `submit_destination_via_outbound_tunnel`, `RouterDeliveryService::deliver_with_transport`, NTCP2's `request_outbound_dial`, and the path peer selector. Enumerate direct transport prerequisites for the *outbound tunnel first hop*, versus the *inbound gateway target behind that outbound route*, and normal peer lookup/background router participation. Source-compare exact unmodified i2pd 2.61.0 `Tunnel::Build` plus IBGW reply behavior, particularly when no outbound exploratory tunnel exists. Define which exception is truly required for initial router bootstrap; a service Destination may not automatically assume that exception.
2. **Design explicit route authority.** Introduce the narrowest typed request policy that distinguishes `RouterBootstrapDirect`, `TunnelFirstHopDirect`, `DestinationRouterDeliveredViaOutbound`, and normal non-destination background NetDB or routing reasons. This need not be a new public API or a new daemon; keep authorizations private at composition/runtime seams. For a normal inbound Destination build, require a live outbound tunnel role and a direct session only to that route's *actual first hop* when needed; the selected inbound gateway is an **encrypted delivery target** behind the route, never the basis for `dial`. If no outbound route exists, fail closed under Plan 478; do not make ordinary inbound direct fallbacks. Handle the distinct source-defined terminal reply route without assuming the terminal must already have a locally initiated session.
3. **Remove illicit eager/indirect dials without global policy breakage.** Replace service startup's `ensure_selected_peer_session(inbound_peers[0])` with correct outbound-first-hop readiness. Apply the same rule to replacement, expiration and replenishment, plus SSU2-to-NTCP2 transport fallback. If a peer happens to be both first-hop and inbound target, attribute any dial to the independently legitimate first-hop route and prevent using that coincidence as an acceptance proof. Retain shared governor accounting, signed RouterInfo validation, cancellation and no unbounded retargeting.
4. **Preserve tunnel/return correctness.** Validate I2NP TunnelData and router-delivery encapsulation, terminal reply handling, authenticated source and reply-ID matching, and the normal Plan 478 route while no direct i2pr→IBGW session is proactively created. Avoid changing tunnel crypto or inventing a garlic/return route inconsistent with stock i2pd. A qualified direct listener reply from the terminal peer may still be accepted if it is legitimate and strictly authenticated; session admission and *locally initiated outbound dial intent* are separate concepts.
5. **Policy mutation and privacy tests.** Fail the pre-fix source path using a fixture that records only actual **dial causes**, not merely sent ShortTunnelBuild packets. Assert a normal inbound build and its replacement generate **zero Destination-purpose direct IBGW dial requests**, but create first-hop direct sessions when required for their outbound role; verify bootstrap-once, absent/stale outbound tunnel fail-closed, SSU2 absent/NTCP2 fallback, simultaneous Destinations, peer overlap, cancellation/restart and selected gateway mismatch. Forbid bypass via `request_outbound_dial`. Tests must not assert that arbitrary independent router background connections to the same peer are invalid. No per-Destination stable telemetry outside the test scope.
6. **Integration gate.** Feed the policy into the existing Plan 478 normal SAM product lane. First require deterministic security regression, then one bounded exact-pinned stock-i2pd attempt only after a source change that actually changes dial authority; do not add a second SAM harness. Ensure Plan 481 first-hop egress receipts and Plan 477 terminal-correlation rules remain intact. Product acceptance remains LS2 owner generation and genuine nonzero-hop bidirectional external SAM STREAM in Plan 478, not this narrow privacy policy alone.
