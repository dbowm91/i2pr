# Plan 329 — Red25519 provenance boundary and normative algorithm freeze

Status: **registered-red25519-clean-room-authority-corrective**

Classification: provenance/security corrective + specification freeze. No production crypto code.

Hard dependencies: none. Historical Plan 325 remains closed blocked and is not rewritten.

## Objective

Correct the forward path after Plan 325 concluded that no maintained Rust Red25519 provider existed.

The new approach is an independent i2pr implementation of the I2P-specific Red25519 construction
over a maintained curve library. The low-level curve implementation remains dependency-owned.

This plan also narrows the Emissary reuse boundary: Red25519 and Encrypted LeaseSet2 crypto source
from the Emissary fork is reference/test-only for this branch and may not be copied or adapted into
i2pr.

## Required work

### 1. Provenance correction

Amend the current project provenance/ADR text so that the Proposal 170 reuse exception does not
cover the Emissary Red25519/ELS2 cryptographic implementation.

Record the distinction explicitly:
- Proposal 170 administrative/domain code may retain its previously authorized provenance rules;
- Red25519/ELS2 crypto code is excluded from direct reuse;
- Emissary may be used only as a post-implementation black-box behavioral oracle for this branch.

Do not rewrite Plan 325 closure. Add a successor note saying its provider-survey result remains
historically true but is no longer the only allowed architectural path.

### 2. Freeze normative specifications

Pin and archive metadata/hashes for:
- I2P Red25519 specification;
- I2P Encrypted LeaseSet specification;
- common structures;
- Proposal 123;
- Proposal 149/new-format B32;
- I2CP fields relevant to encrypted LeaseSets;
- Proposal 170 revision governing the control mapping.

Write a prose algorithm worksheet independent of implementation source.

The worksheet must freeze:
- Ed25519 group/order and byte-order rules;
- type 7 -> type 11 conversion semantics;
- `GENERATE_ALPHA`;
- `BLIND_PRIVKEY`;
- `BLIND_PUBKEY`;
- Red25519 `HStar`, randomized signing and verification equations;
- canonical scalar and point rejection rules;
- storage-key derivation;
- exact official vector inventory;
- encrypted-LS2 outer/middle/inner framing and crypto domains;
- B33 flags/checksum/sigtype encoding;
- PSK and DH client-auth framing/derivations.

### 3. Pin readable reference implementations

Pin:
- Java I2P `93eef5db87fae48025de00c0eb9b669e97b92149`;
- i2pd `2c694149fa6996eaeb23e378d5f83c9d3232c22f`.

Record the exact files allowed as ambiguity/interoperability references.

For Java this includes the blinding, EdDSA blinding, Red key generation, and EncryptedLeaseSet
owners. For i2pd it includes Blinding, Ed25519/signature, LeaseSet and the blinding tests.

Do not translate source text. Any behavior adopted from a reference must be restated in the
algorithm worksheet with its normative/specification basis or explicitly marked as
implementation-dependent compatibility behavior.

### 4. Emissary quarantine for implementation phase

Create a short implementation attestation for Plans 330–334:
- no Emissary Red25519/ELS2 source inspection during production implementation;
- no copied/transliterated constants, comments, tests, or helper layout;
- no fixture generated by reading Emissary internals.

Plan 331 and Plan 335 may run Emissary after the i2pr implementation commit under test is frozen.

### 5. Dependency review

Evaluate direct use of the lockfile’s existing `curve25519-dalek 4.1.3`.

Document required APIs and verify they provide:
- canonical scalar decoding;
- wide reduction;
- Edwards compressed-point decoding;
- basepoint multiplication;
- point addition;
- torsion/small-order checks;
- constant-time arithmetic properties expected by the crate.

Update the intended ADR 0005 amendment, but do not add the direct dependency in this plan.

## Evidence

- exact specification URLs/revisions/hashes;
- algorithm worksheet reviewed independently against both Java and i2pd;
- complete official Red25519 vector manifest;
- direct-dependency review for curve25519-dalek 4.1.3;
- explicit Emissary reference-only boundary;
- no production code or Cargo changes.

## Acceptance criteria

Plan 329 passes when an implementation agent can implement Plan 330 from the frozen worksheet and
normative references without consulting Emissary crypto source and without inventing any
elliptic-curve primitive.

Closure unblocks Plan 330.
