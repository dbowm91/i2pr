# Plan 323 — Canonical TunnelManager envelope and non-deep option parity

Status: **in-progress-prop170-tunnelmanager-canonical-parity**

Classification: capability + protocol reconciliation.

Hard dependency: Plan 320 closed. May execute in parallel with Plans 321 and 325.

## Objective

Make TunnelManager behavior match the canonical Proposal 170 envelope and implement every non-cryptographic parameter that can be supported through existing i2pr owners, while retaining the single M10 ServiceTunnelManager runtime.

## Canonical request model

Implement the exact top-level Proposal fields instead of the former lowercase/nested-options public shape.

Required behavior includes:
- Name and Action;
- All for start/stop/restart;
- Type on create and NewName on edit;
- common Port/TargetHost/Host/TargetPort/TargetDestination/Destination/StartOnLoad/Description/ReachableBy/Shared/UseSSL/tunnel-shaping fields;
- full client proxy, client management, HTTP filter and server option sets;
- LeaseSet fields routed to Plan 326;
- exact aliases only where the Proposal lists aliases.

Conflicting aliases in one request fail before mutation.

## Bulk action semantics

All=true is valid only for start, stop and restart.

Take one bounded snapshot of eligible control-owned/startup-owned tunnels under the ownership rules, apply deterministic ordering, and return per-tunnel results without unbounded fanout.

Define whether startup-owned tunnels are bulk-controllable. The decision must preserve the Plan 289 provenance invariant and be documented in the canonical result.

## Non-deep option owners

Implement or map the remaining Proposal fields that are not cryptographic/LeaseSet/outproxy work, including as applicable:
- Description, ReachableBy, Shared;
- ConnectDelay, DelayOpen;
- Reduce/ReduceCount/ReduceTime;
- Close/CloseTime;
- NewDest and PersistentClientKey lifecycle semantics;
- ProxyList routing input without outproxy-plugin activation;
- ProxyAuth/ProxyUsername/ProxyPassword;
- HTTP AllowUserAgent/AllowReferer/AllowAccept/AllowInternalSSL;
- WebsiteHostname/SpoofedHost;
- BlockAccessInProxies, BlockUserAgents/UserAgents, BlockReferers;
- AccessOption/AccessList/FilterFilePath;
- MaxConcurrentConns and per-client/total minute/hour/day/post/period/ban rate controls;
- SSLProxies/JumpList where they have safe real I2P semantics;
- UseSSL for every Proposal-applicable client/server family.

Each accepted field needs a named runtime owner. Persist-only/inert acceptance is prohibited.

## CustomOptions

Do not treat CustomOptions as an arbitrary bypass around typed validation.

Either:
- parse a documented bounded allowlist into the same typed owners; or
- reject unknown/unsafe keys explicitly.

CustomOptions must never introduce arbitrary filesystem, direct-clearnet, plugin loading, or secret logging capabilities.

## PrivKeyFile

Treat PrivKeyFile as a logical key reference inside an owned key root, not an arbitrary host path. Enforce path confinement/special-file/symlink rules and persistent identity ownership.

## Exact results

Get must emit the exact Proposal info/status structure while filtering secret rawConfig values. Create/edit/start/stop/restart/delete must use exact status/results shape.

## Evidence

Build a generated field×tunnel-type applicability matrix from the canonical inventory and require every cell to be:
- apply with named owner;
- not applicable by Proposal/type;
- deep prerequisite owned by Plans 324/326/327.

No generic “unsupported” bucket may contain non-deep fields at closure.

Test All actions, aliases, conflicts, ranges, rates, persistence/restart, secret redaction, transactional rollback, ownership collisions and all twelve existing backend data paths.

## Acceptance criteria

Plan 323 closes when the canonical TunnelManager public surface is operational for every non-deep field, all twelve types remain real backends, and only destination-algorithm, encrypted-LeaseSet/client-auth, or outproxy-provider cells remain dependency-gated.

Closure unblocks Plans 324 and 327.

- The existing top-level canonical request decoder already validates `All`; Plan 323 now executes start/stop/restart over one sorted, bounded snapshot of control-owned definitions and returns per-tunnel results. Startup-owned TOML definitions are excluded to preserve provenance and mutation ownership. The daemon dispatch no longer substitutes an unavailable marker for these actions.

- This is one Plan 323 slice only. Canonical Get/result shapes, the field×type applicability matrix, and non-deep option ownership remain open; the plan stays in progress and Plans 324/327 stay blocked.
- The existing `ReachableBy` alias is now covered on the canonical black-box lifecycle path: it maps to the real loopback-only listener owner and is returned under the Proposal `reachableBy` key by Get. Focused evidence: `cargo test --locked -p i2pr-daemon --test i2pcontrol_tunnels tunnelmanager_emits_canonical_proposal_result_and_redacts_secrets -- --test-threads=1`. The field remains client-listener applicable only; non-loopback binds continue to fail closed. This does not close the broader field×type matrix or Plan323.

It is excluded from the M10 traffic spec because it describes the tunnel for the manager API, and is bounded both at wire decode and control-spec validation. Focused evidence: `cargo test --locked -p i2pr-daemon --test i2pcontrol_tunnels tunnelmanager_emits_canonical_proposal_result_and_redacts_secrets -- --test-threads=1` and `cargo test --locked -p i2pr-i2pcontrol --test contract plan289_tunnel_request_envelope_rules -- --test-threads=1`.

Proposal integer typing, the existing 1..=128 owner bound, and wire output are covered by the contract, daemon unit, and canonical TunnelManager tests: `cargo test --locked -p i2pr-i2pcontrol --test contract plan289_tunnel_request_envelope_rules -- --test-threads=1`, `cargo test --locked -p i2pr-daemon --lib plan292_shaping_options_have_real_effect -- --test-threads=1`, and `cargo test --locked -p i2pr-daemon --test i2pcontrol_tunnels tunnelmanager_emits_canonical_proposal_result_and_redacts_secrets -- --test-threads=1`.

An explicit value must agree with the complete username/password pair; it is rejected for non-proxy kinds and cannot enable unauthenticated listeners. Contract decoding, daemon owner tests, and `canonical_proxy_auth_uses_owned_credentials_and_redacts_password` cover canonical boolean input, working credentials, contradictory configurations, the canonical Get view, and password redaction.
- The canonical request contract now explicitly verifies that `CustomOptions` cannot act as an arbitrary typed-validation bypass and `PrivKeyFile` cannot accept an arbitrary path; both remain unavailable until a bounded typed allowlist or confined owned key root exists.
- Canonical `MultiHoming` now uses the correctly cased Proposal spelling in the request adapter. Its existing Plan 296 owner is server-only and needs at least two configured targets; the current canonical control model exposes only one target field, so `true` is rejected before mutation until a bounded target-list owner is available. The false value is contract-tested as a typed boolean. Canonical server target, access-list, and `StartOnLoad:false` are exercised by `canonical_server_policy_fields_use_service_tunnel_owners`; Plan 297's existing owner remains authoritative for server `UseSSL`.
- Canonical `Close` and `Reduce` now route to the existing bounded idle lifecycle owner (`close_on_idle` and `reduce_on_idle`) instead of being rejected as ownerless. The owner supplies its existing default deadline when either action is enabled, and the idle sweep performs close or pool reduction. The canonical request contract checks typed mapping, the TunnelManager black-box test checks exact `rawConfig.close`/`rawConfig.reduce` round-trip, and Plan 292 idle-sweep tests cover the runtime effects. `CloseTime`/`ReduceTime` and `ReduceCount` remain separate fields without equivalent bounded runtime owners and are not inferred from this mapping.
- Canonical `Profile` uses the existing bounded streaming-profile owner (`bulk` or `interactive`); the interactive setting configures the service tunnel's streaming window policy. Request decoding and the live TunnelManager Get projection now verify its exact canonical round-trip alongside Close/Reduce.
- Canonical `AllowUserAgent`, `AllowReferer`, and `AllowAccept` now have durable typed HTTP-client owners on `httpclient` and `httpbidirserver`. User-Agent uses the existing keep/stable-replacement policy, Referer maps to the existing strip policy, and Accept has a bounded forwarding flag consumed by the HTTP rewrite path. Other tunnel families reject these fields before mutation. Evidence: `cargo test --locked -p i2pr-i2pcontrol --test contract plan289_tunnel_request_envelope_rules -- --test-threads=1`, `cargo test --locked -p i2pr-service-tunnels proposal_allow_accept_filter_removes_accept_when_disabled -- --test-threads=1`, `cargo test --locked -p i2pr-daemon --lib plan323_http_request_filters_have_a_real_http_client_owner -- --test-threads=1`, `cargo test --locked -p i2pr-daemon --test i2pcontrol_tunnels tunnelmanager_emits_canonical_proposal_result_and_redacts_secrets -- --test-threads=1`, workspace all-target check, and daemon Clippy with warnings denied. - Canonical `CloseTime`, `ReduceTime`, and `ReduceCount` now have independent idle-policy owners. - Canonical `NewDest=0` and `NewDest=2` select ephemeral and persistent client identity policies. `NewDest=1` now requires `Close:true` and selects a separate close-deadline rotation action; only a dedicated ephemeral client is eligible, so shared groups and persistent-key clients are rejected. The legacy Plan 292 `new_dest_on_idle` pool-rebuild action and priority remain unchanged. Plan 323 remains open for its other non-deep fields and the full applicability matrix.
- Canonical `ConnectDelay` now has a bounded generic-client owner. It initiates on the first local TCP read or after the configured 500 ms timeout, and carries at most the advertised Streaming payload in the authenticated SYN; a timeout with no data sends an empty SYN. TCP does not expose the peer application's explicit flush boundary, so the first available read batch is the closest observable trigger. The initial SYN payload is held by the receiver until the application accepts the connection, and outbound oversize input is rejected before queuing. Other tunnel kinds reject the option. Get projects the persisted boolean through the canonical option mapper. Paused-time daemon tests cover first-read triggering, timeout, and the payload ceiling. Evidence: `cargo test --locked -p i2pr-client initial_syn_payload_is_bounded_authenticated_and_delivered_after_accept -- --test-threads=1`, `cargo test --locked -p i2pr-i2pcontrol --test contract plan289_tunnel_request_envelope_rules -- --test-threads=1`, `cargo test --locked -p i2pr-daemon --lib plan323_connect_delay_has_bounded_generic_client_owner -- --test-threads=1`, `cargo test --locked -p i2pr-daemon --lib connect_delay_buffer_tests -- --test-threads=1`, and focused all-target check for daemon, i2pcontrol, service-tunnels, and client. Remaining Plan 323 fields and the full applicability matrix keep the plan active.
- Pinned Java PR6 `DelayOpen` defers `verifySocketManager()` from standard-client startup until `createI2PSocket()`; it controls I2CP session/tunnel startup rather than Streaming SYN timing (`I2PTunnelClientBase.startRunning()` and `createI2PSocket()`). i2pr has no per-service I2CP session: `ServiceTunnelManager::prepare` stages a router-owned `DestinationRuntime` before listener supervisors, and outbound Streaming begins only on an accepted connection (`crates/i2pr-daemon/src/service_tunnels.rs`, `prepare`/`build_service_runtime`/`run_client_loop`). Mapping `DelayOpen` to `ConnectDelay` would change protocol behavior, while storing it without controlling a lifecycle would be inert acceptance. A truthful owner requires a separate design for whether and when a service-owned destination becomes active; Plan 323 remains open for that design and the other uncovered options.
- `ClientPerMinute/Hour/Day` and `TotalInPerMinute/Hour/Day` now configure the authenticated inbound Streaming admission path for generic, HTTP, bidirectional HTTP, and IRC TCP servers. Peer limits key on the authenticated 32-byte Destination hash; total limits are per service. The runtime-neutral owner uses monotonic, fixed minute/hour/day windows, validates the Proposal 0..=100000 bounds, retains at most 4096 peer records, reclaims expired records, and fails closed for new peers at capacity. Canonical decoding and Get return typed integer values; decoder, service policy, daemon owner, black-box Get, peer/aggregate window, and table-cap tests cover the slice. Evidence: `cargo test --locked -p i2pr-i2pcontrol --test contract plan289_tunnel_request_envelope_rules -- --test-threads=1`, `cargo test --locked -p i2pr-daemon --lib plan323_connection_rates_use_authenticated_tcp_server_admission -- --test-threads=1`, `cargo test --locked -p i2pr-daemon --test i2pcontrol_tunnels canonical_server_policy_fields_use_service_tunnel_owners -- --test-threads=1`, and `cargo test --locked -p i2pr-service-tunnels access::tests -- --test-threads=1`. Streamr publisher admission and the separate POST request limits remain without owners, so this does not close Plan 323.
