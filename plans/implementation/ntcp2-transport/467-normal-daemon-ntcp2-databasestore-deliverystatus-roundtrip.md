## Production-reference behavior and proof distinction

Pinned unmodified i2pd 2.61.0 (`PurpleI2P/i2pd@635b013a612ff47278ef02acf8580a28e10e26c5`), `libi2pd/NetDb.cpp::HandleDatabaseStoreMsg`:
- A `DatabaseStore` with nonzero **reply token** includes 4-byte reply tunnel ID and 32-byte reply RouterIdentity hash. If reply tunnel ID is **zero** and token is not the reserved `0xffffffff`, stock i2pd constructs a `DeliveryStatus` for that exact token and calls `transports.SendMessage(replyIdent, deliveryStatus)`.
- The handler sends that acknowledgement **before** its self-RouterInfo early discard, and hence self-RI store can legitimately yield an acknowledgement when explicitly requested. The earlier Plan 455 self-RI message used token **zero**, so no `DeliveryStatus` was owed; retaining that result as failure or as a received reply is incorrect.
- `DeliveryStatus` proves the stock handler parsed the reply-token envelope and a bidirectional authenticated route existed; it **does not** by itself prove a third-party RouterInfo was stored or that the router is usable as a floodfill. A second product-effect test must measure owner mutation if that is the claim.

**Capability:** normal `i2pr run` initiated router-I2NP over NTCP2 receives and correlates genuine stock-originated `DeliveryStatus` through the already implemented shared NetDB/router-I2NP owner. **Infrastructure:** one request correlation holder, bounded live timer/lease, source-accurate socket/session attribution. **Invariant:** same router identity and single product, no public capabilities, no fake response, no new listener or helper-owned transport. **Polish:** a small compact success/failure receipt.
