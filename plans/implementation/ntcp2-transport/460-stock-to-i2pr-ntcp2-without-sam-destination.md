## Distinct evidence tiers

Previously established, do **not** reclassify as untested: `tests/integration/ntcp2/plan455_direct_stock_attempt.sh` authenticated i2pr-initiated NTCP2 and caused unmodified i2pd 2.61.0 to decode a compressed DatabaseStore for its own signed RouterInfo; `tests/integration/ntcp2/plan455_stock_sam_trigger.py` completed exact-byte stock↔stock STREAM in both directions using four independent stock routers with **NTCP2 as the only enabled router transport**. Missing: a **normal stock i2pd process sends I2NP over NTCP2 to a normal `i2pr run` responder**, its authentic receiver/product takes a useful action, and a fresh stock-initiated connection with correctly correlated I2NP reply is independently observed. A response on an already i2pr-initiated session does **not** qualify the fresh stock initiator role.

The pinned source at `PurpleI2P/i2pd@635b013a612ff47278ef02acf8580a28e10e26c5` calls `libi2pd/Transports.cpp::SendMessage -> SendMessages -> PostMessages -> ConnectToPeer` only after a **stock-owned router send** to an eligible signed RouterInfo. Starting an idle daemon and merely importing i2pr's RI cannot cause the missing dial. Use normal reference router source, not a custom transport-linked helper, to find an operation that triggers it.

**Capability:** stock-originated authenticated router I2NP plus response. **Infrastructure:** bounded pristine normal-process driver and topology proof. **Invariant:** peer authenticity, no patched upstream, correct protocol version/address/identity, no fabricated public capabilities. **Polish:** stage-classified sanitized receipts.

## Work packages

1. Reuse Plan 455's isolated normal i2pd launch (distinct 0700 datadirs, explicit CLI `--datadir`/`--conf`, true version/pin), signed and actual-bound `i2pr run` NTCP2 `v=2` RouterAddress from Plan 456 and its exact RouterIdentity, loopback-only authorization, network ID 2 and exact source-pinned address `s`/IV `i`. Import the signed RI into pinned stock NetDB out of band. Check reserved/local-address acceptance, transport preferences, target eligibility, RouterInfo freshness, port and false reachable claims. Do not publish to public I2P.
2. **Tier 1 — normal inbound product**: send a standards-valid i2pd-produced I2NP to an existing authenticated i2pr receiver (possibly on i2pr-initiated session) and independently observe sender emission, receiver authenticated peer, decode and an **owned NetDB/tunnel/control effect** through Plan 459. Where type requires a response, observe it. A self-RI drop without any reply is legitimate but only a receive-only lower-tier proof.
3. **Tier 2 — fresh stock initiator**: using pinned stock `NetDb.cpp`, `ClientContext.cpp`, tunnel scheduler and `Transports.cpp` source, select a stock-owned NetDB or tunnel-build/router-control operation whose target is i2pr's **router identity**, not an I2P client Destination. Accept stock-only SAM as a means to initiate router work **on the stock side**, not as an i2pr SAM tunnel prerequisite. Include sufficient stock peers/floodfills/transit if the operation needs them, but keep i2pr's SAM disabled and do not demand that its client tunnel pool becomes usable. Verify the outgoing peer selection from source/owned events, absent existing stock-to-i2pr session, fresh TCP and NTCP2 handshake, i2pr accepted authenticated link and decoded I2NP product action. Establish a same-trigger stock-to-stock positive control only if necessary to diagnose selector ineligibility; preserve already completed Plan 455 stock control rather than replaying entire harness.
4. **Tier 3 — genuine bidirectional semantics**: send a router-I2NP message requiring a response (e.g. eligible DatabaseLookup) and correlate logical I2NP ID, authenticated peer and link generation across both routers, accounting for any legitimate protocol response path through tunnels rather than assuming an immediate same-link reply. Do not manufacture DeliveryStatus for types that do not require it. Distinguish missing request, ineligible peer, stock send not scheduled, TCP connect, Noise/authentication, decrypted message, owned dispatch, reply generation, reply receipt.
5. Negative controls: network ID, router identity, key/IV, RI signature/host/port/expiry, reservedrange default vs test override, duplicate links, stale send, wrong responder, malformed blocks, rate/queue saturation, link teardown, cancelled deadline, restart and egress profile. Evidence must be finite/redacted counts and opaque per-run digests; no raw router hashes/private keys/RouterInfo/stock logs persisted. Pin absence in deliberate integration lane is a hard error, not a silent skip.
